# 06 — ทบทวน Scope: อะไรตัดได้ อะไรต้องเอาเข้าระบบ

หลังได้เห็นฟอร์มจริง 2 ใบ (`QC-F006-V00` ใบแจ้งการร้องเรียนและการคืนสินค้า และ `INSPECTION REPORT`)
จึงทบทวน scope ใหม่ทั้งหมดตามหลัก **"อะไรซ้ำซ้อนให้ตัด อะไรที่ยังทำมือให้เข้าระบบ"**

---

## 1. หลักที่ใช้ตัดสิน

| ถ้า... | ให้... |
|---|---|
| ข้อมูลมีอยู่ใน SAP แล้ว | **อย่าเก็บซ้ำ** — อ้างอิงด้วยเลขเอกสารพอ |
| คนกรอกข้อมูลเดียวกันสองรอบ | **กรอกครั้งเดียว แล้วให้ระบบสร้างเอกสารที่เหลือ** |
| ตารางหนึ่งคำนวณจากอีกตารางได้ | **ตัดทิ้ง คำนวณเอาตอนใช้** |
| งานที่ยังทำด้วยมือและตกหล่นบ่อย | **เอาเข้าระบบ** |
| ฟีเจอร์ที่ยังไม่มีใครร้องขอ | **อย่าเพิ่งทำ** |

## 2. สิ่งที่ตัดออก

### 2.1 ตัดตาม feedback: เก็บเฉพาะ PO ที่เซ็นแล้ว

| เดิม | ใหม่ |
|---|---|
| เก็บ **PO** (ตอนเปิดใน SAP) และ **PO ที่ซัพเซ็นกลับ** = 2 ไฟล์ | เก็บ **PO ที่เซ็นครบแล้ว** ใบเดียว |

**เหตุผล:** PO ที่ยังไม่เซ็นมีอยู่ใน SAP อยู่แล้ว การเก็บทั้งสองใบทำให้มีสองเวอร์ชันของเอกสารเดียวกัน
แล้วคนจะหยิบผิดใบตอนส่งให้บัญชีหรือตอนตรวจสอบ — เลขที่ PO ยังบันทึกในระบบเหมือนเดิม แค่ไม่เก็บไฟล์ที่ยังไม่สมบูรณ์

### 2.2 ตัดตาราง 4 ตาราง

| ตาราง | ตัดเพราะ | แทนด้วย |
|---|---|---|
| `Deal_Stages` | 17 แถวต่อดีล แต่ข้อมูลทุกอย่างซ้ำกับ `Stage_Log` ที่บันทึกทุกการเปลี่ยนอยู่แล้ว | `current_stage` บน `Deals` + คำนวณประวัติจาก `Stage_Log` |
| `Match_Check` | เป็นผลลัพธ์ที่คำนวณได้ ไม่ใช่ข้อมูลต้นทาง | 3 คอลัมน์บน `Deals`: `match_ready`, `match_diff`, `match_block` |
| `Physical_Docs` | ผูก 1:1 กับเอกสารหนึ่งใบอยู่แล้ว | 4 คอลัมน์บน `Doc_Checklist`: `tracking_no`, `sent_at`, `received_by`, `received_at` |
| `Suppliers` (แบบเต็ม) | master จริงอยู่ใน SAP | เหลือ 4 คอลัมน์เท่าที่ต้องใช้ส่งอีเมล: `code`, `name`, `contact_email`, `contact_line` |

**ผลลัพธ์: 15 ตาราง → 13 ตาราง ทั้งที่เพิ่มความสามารถใหม่ 2 อย่าง**

### 2.3 ไม่ทำ (ยัง)

ระบุไว้ชัดเพื่อกัน scope บาน — ทำเมื่อมีคนร้องขอจริงเท่านั้น

`สต๊อก/ต้นทุน` · `ทำจ่ายเงินจริง` · `landed cost` · `sync SAP อัตโนมัติ` ·
`ลายเซ็นดิจิทัลที่มีใบรับรอง CA` · `หลายสกุลเงิน` · `แอปมือถือแยก` (ใช้เว็บบนมือถือ)

## 3. สิ่งที่เอาเข้าระบบเพิ่ม

### 3.1 ใบขอเปิดรหัสสินค้าใหม่ — เดิมเป็นกระดาษ

```
เดิม  SR เขียนใบขอ → พิมพ์ → SR Head เซ็น → เดินเอกสารไปให้ LS → LS คีย์เข้า SAP
      → บอกกลับทางไลน์ → SR เปิด PO
ใหม่  SR กรอกในระบบ → SR Head กดอนุมัติ → เข้าคิว LS อัตโนมัติ
      → LS เปิดใน SAP แล้วบันทึกรหัสกลับ → ดีลเดินต่อเอง
```

ฟิลด์: ชื่อสินค้า · แบรนด์ · กลุ่มสินค้า · หน่วยนับ · ขนาดบรรจุ · ซัพพลายเออร์ ·
พิกัดศุลกากร · การเก็บรักษา · อายุสินค้า · ดีลที่เกี่ยวข้อง · เหตุผล

**กติกาที่เพิ่มมา:** ดีลจะข้ามขั้น `ITEM_CODE` ไม่ได้จนกว่าจะมีรหัสจริงจาก SAP กลับมา —
กันเคสที่ตอนนี้เปิด PO ไปก่อนแล้วรหัสยังไม่มา

### 3.2 ใบเคลม / ใบแจ้งการร้องเรียน — ตามฟอร์ม QC-F006-V00

ทำตามโครงฟอร์มเดิมทุกส่วน ไม่เปลี่ยนวิธีทำงาน เปลี่ยนแค่ที่กรอก:

| ส่วน | ผู้ดำเนินการ | ระบบช่วยอะไร |
|---|---|---|
| **ส่วนที่ 1** การร้องเรียน | Sales Coordinator | ดึง ชื่อสินค้า/แบรนด์/Lot/คลัง/Packing จากเลข **PI/DN** ที่กรอก แทนพิมพ์เอง |
| **ส่วนที่ 2** ผลการตรวจ | QC | ผลตรวจ ผ่าน/ไม่ผ่าน + แนบรูป · **ไม่ผ่าน → เปิดส่วนที่ 3 ให้เอง** |
| **ส่วนที่ 3** เคลมกับผู้ขาย | SR + Procurement Manager | ผูกกับ PO ซัพ · เมื่อได้ใบลดหนี้ → **ปลดล็อกการจ่ายเงินอัตโนมัติ** |

ลายเซ็น 5 ตำแหน่งตามฟอร์มเดิม (QC · Procurement Manager · ผู้ออกเอกสาร · ผู้รับทราบ · ผู้ขาย)
เก็บเป็นหลักฐานอิเล็กทรอนิกส์ตาม [เอกสาร 04 §5](04-automation-approval.md)

> **ยังต้องยืนยัน:** ส่วนที่ 3 ในไฟล์ต้นฉบับอยู่หน้า 2–3 ซึ่งเป็นภาพสแกน อ่านข้อความไม่ได้
> ผมทำตามที่อนุมานจากส่วนที่ 2 ที่เขียนว่า "ไม่ผ่าน (ดำเนินการส่วนที่ 3)" — **ขอฟิลด์จริงของส่วนที่ 3 ด้วย**

### 3.3 การซ้ำซ้อนที่เจอในฟอร์มจริง — QC กรอกข้อมูลเดียวกัน 2 รอบ

เทียบสองฟอร์มที่ได้มา พบว่าข้อมูลชุดเดียวกันถูกกรอกซ้ำ:

| ข้อมูล | อยู่ในใบร้องเรียน ส่วนที่ 2 | อยู่ใน INSPECTION REPORT |
|---|---|---|
| ชื่อสินค้า | ✓ | ✓ Products |
| Lot | ✓ | ✓ Lot No. `C260225 #1` |
| ผู้ขาย | ✓ | ✓ Supplier |
| สถานที่ตรวจ | ✓ คลังโชติ | ✓ Inspection Location `Chod Warehouse` |
| วันที่ตรวจ | ✓ | ✓ Date |
| อ้างอิงเอกสาร | ✓ PI | ✓ Reference Document `PI No. F12607001` |
| รายละเอียดข้อบกพร่อง | ✓ | ✓ Defect Details |
| ลงนาม QC + Procurement Manager | ✓ | ✓ |

**ทั้งสองใบใช้ข้อมูลชุดเดียวกันเกือบทั้งหมด** → ในระบบให้ QC กรอกครั้งเดียวในส่วนที่ 2
แล้ว **ระบบสร้าง INSPECTION REPORT เป็น PDF ตามฟอร์มเดิมให้** (Po Ref No., Doc Date, Sampling plan,
Number of samples, Inspection Location, Summary of results, Defect Details, ช่องลงนาม)

นี่คือการลดงานที่วัดผลได้ทันที: **จากกรอก 2 ใบ เหลือ 1 ใบ ต่อการเคลมหนึ่งครั้ง**

### 3.4 อื่น ๆ ที่ยังทำมืออยู่

| งานที่ทำมือ | เข้าระบบเป็น |
|---|---|
| SR แจ้ง Effective date ให้ AC ทางเมล | ฟิลด์บนดีล — AC เห็นเอง |
| SR จำ payment condition เพื่อตามใบแจ้งหนี้ | ระบบคำนวณวันครบกำหนดแล้วเตือน |
| ตามเอกสารตัวจริงที่ส่งไปรษณีย์ | เลข tracking + ผู้รับ บน checklist |
| สแกนและรวมไฟล์ตอนปิดงาน | อัพครั้งเดียวตอนเอกสารเกิด ไม่ต้องรวมทีหลัง |
| ได้ใบลดหนี้แล้วบอกบัญชีให้จ่ายได้ | บันทึกใบลดหนี้ → ปลดล็อกการจ่ายอัตโนมัติ |

## 7. ที่ยังต้องการจากทีม

1. **ฟิลด์จริงของส่วนที่ 3** ในฟอร์ม QC-F006 (หน้า 2–3 เป็นภาพสแกน อ่านไม่ได้)
2. ใบเคลมกับ**ผู้ขาย** ใช้ฟอร์มเดียวกับใบร้องเรียน**ลูกค้า** หรือมีฟอร์มแยก

5. ยืนยันว่า **ตัด PO ที่ยังไม่เซ็นออกได้จริง** ไม่มีขั้นตอนไหนต้องใช้

## 8. ปรับตามรอบทบทวนที่สอง — ให้เข้าใจง่ายและใกล้ ERP

### 8.1 `Deal` → `PO`

เลิกใช้คำว่า "ดีล" ทั้งระบบ ใช้ **PO (ใบสั่งซื้อ)** ซึ่งเป็นคำที่ทุกแผนกใช้อยู่แล้ว
ไม่ต้องเรียนศัพท์ใหม่ · ตาราง `Deals` → **`Purchase_Orders`** · `deal_no` → `po_no`

| | เดิม | ใหม่ |
|---|---|---|
| ตาราง | `Deals` | `Purchase_Orders` |
| เลขที่ | `D-26-0042` | `PO-26-0042` |
| เลข SAP | `sap_po_no` | `sap_po_no` (เหมือนเดิม) |

### 8.2 หนึ่ง PO จ่ายได้หลายงวด — ตาราง `PO_Payments` ใหม่

ของจริงจ่าย 2 รอบ (มัดจำ + ส่วนที่เหลือ) แต่โครงเดิมมีสลิปใบเดียวต่อ PO ซึ่งผิด

`payment_id` · `po_no` · `seq` · `payment_type` (`DEPOSIT / BALANCE / FULL`) · `percent` ·
`amount` · `currency` · `due_date` · `status` (`PENDING / BLOCKED / PAID / CANCELLED`) ·
`paid_at` · `slip_doc_id` · `bank_ref` · `paid_by` · `note`

ผลที่ตามมา:

- **สลิปย้ายออกจาก checklist ของ PO** ไปผูกกับงวดจ่ายแทน — 2 งวดก็มี 2 สลิป
- ระบบเตือนบัญชี**ตามวันครบกำหนดของแต่ละงวด** ไม่ใช่ครั้งเดียวต่อ PO
- เคลมล็อกได้**เฉพาะงวดที่ยังไม่จ่าย** (`BLOCKED`) งวดที่จ่ายไปแล้วไม่กระทบ
- ปิด PO ได้ต่อเมื่อ**ทุกงวดเป็น `PAID`**

### 8.3 แยก "เสร็จสิ้น" ออกจากหน้าจอหลัก

`Purchase_Orders.status` = `ACTIVE / COMPLETED / CANCELLED`

หน้ารายการ PO แยกเป็น 3 แท็บ + แท็บค้นหา — หน้าจอที่ใช้ทุกวันเห็นเฉพาะ `ACTIVE`
ของที่ปิดแล้วยังค้นเจอได้แต่ไม่มารกตา

### 8.4 ยุบ 17 ขั้นเหลือ 4 เฟส (สำหรับการมองเห็น)

17 ขั้นตอนถูกต้องแต่**ดูแล้วท่วม** จึงจัดกลุ่มเป็น 4 เฟสในหน้าจอ ส่วนขั้นย่อยยังอยู่ครบ
เปิดดูได้ในแท็บย่อย — ข้อมูลไม่ได้ลดลง แค่ลำดับการมองเห็นเปลี่ยน

| เฟส | ครอบขั้นที่ | ความหมาย |
|---|---|---|
| **จัดซื้อ** | 1–9 | เช็คราคา → อนุมัติ → ผู้ขายเซ็น PO กลับ |
| **รับของ** | 10–12 | จองรถ → QC ตรวจรับ → GR |
| **ตั้งหนี้** | 13–14 | ใบแจ้งหนี้ → ส่งมอบเอกสาร |
| **จ่าย / ปิด** | 15–17 | จ่ายทุกงวด → ใบเสร็จ → ตรวจ 3 ทาง → ปิด |

`Stage_Templates` เพิ่มคอลัมน์ `phase_code` เพียงคอลัมน์เดียว ไม่ต้องแก้อย่างอื่น
