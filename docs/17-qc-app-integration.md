# 17 · เชื่อมกับแอปตรวจรับของ QC ซึ่งเป็นเว็บแอปคนละตัว

> คำถามจากทีม: *"แอปส่งข้อมูลออกจากอีก web app นึง จะเชื่อมต่อกันอย่างไร"*

## สรุปคำตอบใน 5 บรรทัด

1. **ไม่ต้องรวมสองระบบเป็นระบบเดียว** — แอป QC เก็บใบตรวจฉบับเต็มไว้ที่เดิม ระบบนี้ขอแค่ **หัวใบกับสรุปผล**
2. เชื่อมด้วย **2 ทางคู่กัน** — แอป QC **ส่งมาเอง (push)** ตอนกดจบใบ + ระบบนี้ **ไล่เก็บย้อนหลัง (pull)** ทุก 30 นาที
3. ยืนยันตัวตนด้วย **กุญแจลับร่วม + ลายมือชื่อ HMAC** ไม่ใช่ token ลอยบน URL
4. **ถ้าทีมแอป QC ยังแก้อะไรไม่ได้ ระบบนี้ก็เดินได้อยู่แล้ว** — การเชื่อมคือการลดงานพิมพ์ซ้ำ ไม่ใช่เงื่อนไขว่าระบบจะทำงานได้
5. **จุดที่พังจริงไม่ใช่ "ส่งไม่ถึง" แต่คือ "ส่งถึงแล้วไม่รู้ว่าของใบไหน"** — ต้องมีคิวให้คนจับคู่ ไม่ใช่ให้ระบบเดา

## 1. เลือกวิธีเชื่อมจากสิ่งที่แอป QC ทำได้

ตอบ 3 คำถามนี้แล้วจะรู้ว่าต้องใช้ทางไหน ไม่ต้องเลือกจากความชอบ

```
แอป QC อยู่บน Google Workspace เดียวกัน และเก็บข้อมูลใน Google Sheet ?
├─ ใช่  → ทาง A: อ่านชีตตรง ๆ  (ง่ายที่สุด ไม่ต้องเขียน API เลย)
└─ ไม่  → แอป QC เรียก URL ภายนอกได้ไหม (ตอนกดจบใบ) ?
          ├─ ได้    → ทาง B: push + pull   ◀── แนะนำ
          └─ ไม่ได้ → แอป QC มี API ให้อ่านไหม ?
                      ├─ มี    → ทาง C: pull อย่างเดียว
                      └─ ไม่มี → ทาง D: ส่งออกไฟล์ลงโฟลเดอร์ Drive ตามเวลา
                                 └─ ทำไม่ได้อีก → ทาง E: พิมพ์เลขใบตรวจเอง (ที่ใช้อยู่ตอนนี้)
```

| ทาง | ต้องแก้อะไรในแอป QC | ข้อมูลถึงเมื่อไหร่ | งานพิมพ์ซ้ำ |
|---|---|---|---|
| **A · อ่าน Google Sheet ร่วมกัน** | แค่กด **แชร์ชีต** ให้บัญชีบริการของระบบนี้ | ทันทีที่อ่าน (ทุก 5–30 นาที) | ไม่มี |
| **B · push + pull** ◀ แนะนำ | เพิ่มโค้ดยิง `UrlFetchApp` ~20 บรรทัด ตอนกดจบใบ | **ไม่กี่วินาที** | ไม่มี |
| C · pull อย่างเดียว | เปิด endpoint ให้อ่านตามช่วงเวลา | ช้าสุด 30 นาที | ไม่มี |
| D · ส่งออกไฟล์ | ตั้ง job ส่งออก CSV/JSON ลงโฟลเดอร์ Drive | ตามรอบที่ตั้ง | ไม่มี |
| E · พิมพ์เอง (ตอนนี้) | **ไม่ต้องแก้อะไรเลย** | ทันทีที่ QC พิมพ์ | QC พิมพ์ 6–10 ช่อง |

> **ถ้าแอป QC เป็น Apps Script + Google Sheet เหมือนระบบนี้ → ใช้ทาง A ได้เลย**
> ไม่ต้องทำ API ไม่ต้องมีกุญแจ ไม่ต้องมี webhook — แค่แชร์ชีตแล้วอ่านด้วย `SpreadsheetApp.openById()`
> เป็นทางที่ถูกและพังยากที่สุด ควรเช็คข้อนี้ก่อนเสมอ

## 2. ทางที่แนะนำ (B) — ส่งมาเอง + ไล่เก็บย้อนหลัง

### ทำไมต้องสองทาง

| ใช้ทางเดียว | ปัญหา |
|---|---|
| push อย่างเดียว | เน็ตหลุดครั้งเดียว **ใบนั้นหายเงียบ ๆ** ไม่มีใครรู้ว่าหาย |
| pull อย่างเดียว | ช้าสุด 30 นาที คลังที่ยืนรอรับของอยู่หน้าห้องเย็นรอไม่ได้ |

**push ให้เร็ว · pull เป็นตาข่ายรองรับ** — pull ไม่ได้เอาไว้ใช้งานปกติ แต่เอาไว้ซ่อมของที่ push หาย
ถ้า pull เจอใบที่ไม่เคยเข้ามา แปลว่า push พัง ระบบขึ้นเตือนแอดมินให้รู้

```
แอป QC (เว็บแอปอีกตัว)                       MGS Document Hub
─────────────────────                       ────────────────────
กด "จบใบตรวจ"
  │
  ├─(1) บันทึกใบในระบบตัวเองให้เสร็จก่อน  ← สำคัญ: ไม่รอเรา ไม่ต้องแคร์ว่าเราล่ม
  │
  └─(2) POST /exec?fn=qcReport ─────────────▶ ตรวจลายมือชื่อ + เวลา
         { reportNo, version, module, … }      │
                                               ├─ ซ้ำ (เลข+version เดิม) → ตอบ ok เฉย ๆ
                                               ├─ จับคู่รายการได้    → ลงข้อมูล + แจ้งคลัง
                                               └─ จับคู่ไม่ได้       → เข้าคิวให้คนจับคู่
         ◀──────────────── 200 {"ok":true}
       (ส่งไม่ผ่าน → เข้าคิวส่งใหม่ 1/5/30 นาที)

ทุก 30 นาที (ตัวตั้งเวลาฝั่งเรา)
         GET /api/reports?since=… ───────────▶ เทียบกับที่มีอยู่
         ◀─── รายการใบตรวจตั้งแต่เวลานั้น      └─ ใบไหนยังไม่มี = push หาย → เก็บเข้ามา + เตือนแอดมิน
```

### หน้าตาข้อมูลหนึ่งใบ (สัญญาระหว่างสองระบบ)

ช่องกลางเหมือนกันทุกสายสินค้า ส่วนที่ต่างกันอยู่ใน `extra` — **เพิ่มสายใหม่ไม่ต้องแก้สัญญา**

```json
{
  "reportNo":     "F-2026049",
  "version":      1,
  "module":       "FOOD",
  "poRef":        "PO-F126050010",
  "docDate":      "2026-08-19",
  "inspectedAt":  "2026-08-14",
  "location":     "Ruxchai Cold Storage II",
  "supplier":     "GLORYHONG FOOD CO.,LIMITED",
  "invQty":       "2600 CTN",
  "actualQty":    "2600 CTN",
  "result":       "PASS",
  "rejectQty":    "",
  "extra":        { "temp": -20.0, "lot": "126005711", "expiry": "2028-06", "grade": "A" },
  "defects": [
    { "text": "พบกล่องบุบ เสียรูป และมีร่องรอยความชื้น",
      "remark": "รอสรุปเรื่องเปลี่ยนกล่อง", "blocksPayment": true },
    { "text": "พบขนาดกล่องไม่เท่ากัน",
      "remark": "ให้ฝ่ายขายตั้งราคาตามขนาด", "blocksPayment": false }
  ],
  "reportUrl":    "https://qc-app…/report/F-2026049",
  "signedBy":     { "qc": "Kritiyanee S.", "procurement": "Khanittha P." },
  "sentAt":       "2026-08-19T10:22:31+07:00"

```

ฝั่งเครื่องจักรส่ง `"module":"MECH"` และ `"extra":{ "conCondition":"PASS" }` — **ไม่มี** temp / lot / expiry

**หน่วยนับต้องเว้นวรรคระหว่างตัวเลขกับหน่วย** (`2600 CTN` ไม่ใช่ `2,600CTNs`)
ระบบปลายทางรองรับ `CTNs/cartons/กล่อง → CTN` และ `KGS/กก. → KG` ให้อยู่แล้ว แต่ส่งมาสะอาดตั้งแต่ต้นดีกว่า

## 3. โค้ดสองฝั่ง (Apps Script)

### ฝั่งแอป QC — เรียกตอนกดจบใบ

```js
const HUB_URL = 'https://script.google.com/a/macros/…/exec';
const HUB_KEY = PropertiesService.getScriptProperties().getProperty('HUB_KEY');

function sendToHub_(report) {
  const body = JSON.stringify(report);
  const sig  = Utilities.base64Encode(
    Utilities.computeHmacSha256Signature(body, HUB_KEY));   // ลายมือชื่อบนเนื้อข้อมูล
  try {
    const res = UrlFetchApp.fetch(HUB_URL + '?fn=qcReport', {
      method: 'post', contentType: 'application/json', payload: body,
      headers: { 'X-MGS-Signature': sig }, muteHttpExceptions: true
    });
    if (res.getResponseCode() === 200) return true;
    queueRetry_(report);          // ไม่ 200 = เข้าคิวส่งใหม่
  } catch (e) {
    queueRetry_(report);          // เน็ตหลุด = เข้าคิวส่งใหม่
  }
  return false;
}
```

**สำคัญ: บันทึกใบในแอป QC ให้เสร็จก่อนแล้วค่อยเรียก** — ถ้าเรียกก่อนบันทึก แล้วระบบเราล่ม
QC จะกดจบใบไม่ได้ กลายเป็นระบบเราไปขวางงานเขา ซึ่งรับไม่ได้

คิวส่งใหม่ใช้ trigger ธรรมดา ลองที่ 1 / 5 / 30 นาที ครบ 3 ครั้งแล้วปล่อย — เพราะ pull จะเก็บให้เอง

### ฝั่ง Document Hub — รับ

```js
function doPost(e) {
  const raw = e.postData.contents;
  const sig = Utilities.base64Encode(
    Utilities.computeHmacSha256Signature(raw, KEY));
  if (sig !== e.parameter.sig && sig !== (e.headers || {})['X-MGS-Signature'])
    return json_({ ok:false, err:'bad signature' });

  const r = JSON.parse(raw);
  if (Math.abs(Date.now() - new Date(r.sentAt)) > 5*60*1000)
    return json_({ ok:false, err:'stale' });          // กันเอาก้อนเดิมมายิงซ้ำภายหลัง

  const lock = LockService.getScriptLock(); lock.waitLock(20000);
  try {
    const key = r.reportNo + '#' + r.version;
    if (seen_(key)) return json_({ ok:true, dup:true });   // ส่งซ้ำกี่ครั้งผลเท่าเดิม
    saveReport_(r);
    const deal = matchDeal_(r);                            // §4
    if (deal) applyToDeal_(deal, r); else queueForHuman_(r);
    return json_({ ok:true, matched: !!deal });
  } finally { lock.releaseLock(); }
}
```

`applyToDeal_` ทำ 3 อย่าง — ลงช่องในสัญญาส่งมอบขั้น QC · แปลง `defects` เป็น**ข้อค้าง** (ข้อที่
`blocksPayment` ล็อกงวดจ่ายทันที ดู [docs/16 §2](16-qc-report-mapping.md)) · แจ้งคลังกับบัญชี

### ถ้าใช้ทาง A (ชีตร่วมกัน) — สั้นกว่ามาก

```js
function pullFromQcSheet_() {
  const sh   = SpreadsheetApp.openById(QC_SHEET_ID).getSheetByName('Reports');
  const rows = sh.getDataRange().getValues();
  const head = rows.shift();
  rows.filter(r => r[head.indexOf('updated_at')] > lastSync_())
      .forEach(r => ingest_(rowToReport_(head, r)));
}
```

ไม่มีกุญแจ ไม่มีลายมือชื่อ ไม่มี endpoint — สิทธิ์คุมด้วยการแชร์ชีตตามปกติของ Google

## 4. ปัญหาที่ยากที่สุด: จับคู่ใบตรวจกับรายการ

ไม่ใช่เรื่องเทคนิคการส่ง แต่คือ **ส่งถึงแล้วไม่รู้ว่าเป็นของรายการไหน**

หลักฐานจากใบจริง — ใบ **M-2026097**

| ที่ | เลขที่เขียนไว้ |
|---|---|
| หัวใบ · PO Ref No. | `M-RC26200090` |
| ใบรับสินค้าที่แนบข้างใน · PO | `M-3026064` |

**คนละเลข ทั้งที่เป็นใบเดียวกัน** — ฝั่งอาหารใช้ `PO-F126050010` ซึ่งก็ไม่ใช่ DocNum ของ B1

### วิธีจับคู่ (ทำตามลำดับ หยุดที่ข้อแรกที่เจอ)

1. `poRef` ตรงกับเลข PO ใน B1 หรือเลขรายการในระบบ → ผูกเลย
2. `poRef` ตรงกับ **ตารางเทียบเลขที่เคยจับคู่ไว้แล้ว** → ผูกเลย
3. ผู้ขาย + สินค้า + ช่วงวันที่ตรงกัน **และเจอรายการเดียวเท่านั้น** → ผูก แล้วบันทึกว่าเดามาจากอะไร
4. **ไม่เข้าข้อไหนเลย → เข้าคิวให้คนจับคู่ ห้ามเดา**

> **ห้ามเดาตอนจับคู่ไม่ได้** — จับผิดใบแปลว่าเอาผลตรวจของล็อตหนึ่งไปตั้งหนี้อีกล็อตหนึ่ง
> เสียหายกว่าปล่อยให้ค้างคิว 10 นาทีมาก

คิวจับคู่อยู่ที่ **ตั้งค่าระบบ → เชื่อมแอปตรวจรับ QC** (กดดูได้ในตัวอย่างระบบ)
เลือกรายการแล้วกดผูก → **ช่องทั้งหมดลงให้เอง QC ไม่ต้องพิมพ์ซ้ำ** และ**จำการจับคู่ไว้**
ครั้งหน้าเลขชุดเดียวกันจับได้เอง (ข้อ 2)

**สิ่งที่ควรขอจากทีมแอป QC:** ส่ง**ทั้งสองเลข**มาด้วยกัน (`poRef` + `receiptRef`)
ถ้าทำได้ ข้อ 4 แทบไม่เกิดเลย

## 5. กรณีที่ต้องคิดไว้ก่อน ไม่ใช่มาเจอตอนใช้จริง

| กรณี | ระบบทำอะไร |
|---|---|
| **ส่งซ้ำใบเดิม** | กันด้วย `reportNo + version` — ส่งกี่ครั้งผลเท่าเดิม ตอบ `ok` ไม่แจ้งเตือนซ้ำ |
| **ออกใบแก้ (version 2)** | ทับของเดิม + บันทึกว่าใบถูกแก้ + แจ้งคนที่ใช้ผลนั้นไปแล้ว |
| **ออกใบแก้หลังจ่ายเงินไปแล้ว** | **ระบบไม่กลับรายการเอง** — ขึ้นเตือนบัญชีกับจัดซื้อให้ตัดสินใจ การกลับรายการเงินต้องมีคนรับผิดชอบเสมอ |
| **ระบบนี้ล่ม** | QC กดจบใบในแอปตัวเองได้ตามปกติ · ใบเข้าคิวส่งใหม่ · ที่หลุดจริง pull เก็บให้ |
| **แอป QC ล่ม** | ระบบนี้ยังเดินได้ — QC พิมพ์เลขใบตรวจเข้ามาเองเหมือนที่ทำอยู่ทุกวันนี้ |
| **ใบตรวจมาถึงก่อนรายการจะเดินถึงขั้น QC** | เก็บไว้ก่อน พอถึงขั้น QC ช่องกรอกมาเองแล้ว |
| **ใบตรวจไม่มีรายการรองรับเลย** (ของมาโดยไม่มี PO) | ค้างคิวจับคู่ · เป็นสัญญาณว่ามีของเข้าโดยไม่ผ่านจัดซื้อ ควรตามให้จบ |
| **กุญแจลับหลุด** | เปลี่ยนกุญแจได้โดยไม่ต้องหยุดระบบ — รองรับกุญแจเก่ากับใหม่พร้อมกันช่วงเปลี่ยน |
| **ใบเดียวกันถูกยิงจากสองที่** | ล็อกด้วย `LockService` ตอนบันทึก ไม่งั้นข้อค้างจะซ้ำสองชุด |

## 6. ลำดับการทำ

| ขั้น | ทำอะไร | ใช้เวลา | ระบบใช้งานได้ไหมระหว่างนี้ |
|---|---|---|---|
| 0 | **ตอนนี้** — QC พิมพ์เลขใบตรวจ + สรุปสั้น ๆ เอง | — | ✅ ใช้ได้เต็มรูปแบบ |
| 1 | ถามทีมแอป QC 3 คำถามใน §1 แล้วเลือกทาง A–E | 1 วัน | ✅ |
| 2 | ตกลงหน้าตาข้อมูล (§2) + แลกกุญแจ + ทำ endpoint ทดสอบ | 2–3 วัน | ✅ |
| 3 | ต่อ **pull** ก่อน — ไม่ต้องแก้อะไรในแอป QC เลยถ้าเป็นทาง A/C | 2 วัน | ✅ ข้อมูลเริ่มลงเอง |
| 4 | ต่อ **push** เพื่อให้ข้อมูลถึงเร็ว | 2 วัน | ✅ |
| 5 | เปิดคิวจับคู่ให้แอดมินใช้จริง + สะสมตารางเทียบเลข | ต่อเนื่อง | ✅ |

**ทุกขั้นทำแล้วระบบยังใช้งานได้ ไม่มีขั้นไหนที่ต้องหยุดใช้ระบบเพื่อรอการเชื่อม**
และถ้าติดที่ขั้นไหน หยุดตรงนั้นได้เลย ของที่ทำไปแล้วยังใช้ได้

## 7. เรื่องที่ต้องตกลงกับทีมแอป QC

| ระดับ | เรื่อง | ทำไมต้องตกลงก่อน |
|---|---|---|
| **ติดจริง** | แอป QC เรียก URL ภายนอกได้ไหม | ถ้าไม่ได้ ต้องเปลี่ยนเป็นทาง A / C / D ทั้งหมด |
| **ติดจริง** | ฝั่ง Mech จะจับคู่ด้วยอะไร | `M-RC26200090` กับ `M-3026064` คนละชุด — ขอให้ส่งทั้งสองเลข |
| ต้องคุย | ออกใบแก้ย้อนหลังได้ไหม รู้ได้อย่างไร | ต้องมี `version` ไม่งั้นใบแก้จะทับเงียบ ๆ |
| ต้องคุย | ตาราง Defect & Remark ส่งเป็นข้อมูลได้ไหม | ถ้าได้แค่ข้อความก้อนเดียว ระบบตัดบรรทัดให้ แต่ต้องมีคนติ๊กว่าข้อไหนล็อกเงิน |
| ต้องคุย | รูปถ่ายในใบ | ขอเป็นลิงก์พอ — ใบอาหารใบเดียว 24 หน้าส่วนใหญ่เป็นรูป ก๊อปมาเก็บซ้ำเปลืองที่เปล่า ๆ |
| ตกลงได้เลย | วิธียืนยันตัวตน | กุญแจลับร่วม + HMAC-SHA256 + ประทับเวลา ±5 นาที |
| ตกลงได้เลย | แอป QC ต้องรอเราตอบไหม | **ไม่ต้อง** — ส่งแล้วจบ ระบบเราต้องไม่ขวางงาน QC |

## 8. ดูของจริงได้ที่ไหน

ในตัวอย่างระบบ: **ตั้งค่าระบบ → เชื่อมแอปตรวจรับ QC**

- วิธีเชื่อมทั้งสองทาง + วิธียืนยันตัวตน + กติกากันซ้ำ/ส่งใหม่
- **คิวใบตรวจที่จับคู่ไม่ได้** — มีใบตัวอย่าง 2 ใบ ลองเลือกรายการแล้วกดผูก
  จะเห็นว่าช่องของขั้น QC ลงให้เองทั้งหมด และข้อค้างท้ายใบตามมาด้วย
- หน้าตาข้อมูลที่ส่งกันหนึ่งใบ + ตารางว่าแต่ละช่องปลายทางเอาไปทำอะไร
- รายการเรื่องที่ต้องตกลงกับทีมแอป QC แยกเป็น *ติดจริง / ต้องคุย / ตกลงได้เลย*

## 9. ทดสอบแล้ว

```
node tools/smoke.js       # 287 เรนเดอร์ + เคสเชื่อมแอป QC → ผ่าน
node tools/walkthrough.js # เดินครบ 13 ขั้น
```

เคสที่เพิ่ม

- หน้าเชื่อมแอป QC บอกวิธีเชื่อม วิธียืนยันตัวตน และหน้าตาข้อมูลที่ส่งกัน
- ใบตรวจที่จับคู่ไม่ได้ต้องเข้าคิว **ทั้งฝั่งอาหารและฝั่งเครื่องจักร**
- กดผูกโดยไม่เลือกรายการ → **ระบบต้องไม่เดาให้**
- ผูกใบแล้ว → เลขใบตรวจ จำนวนที่นับได้ สถานที่ตรวจ **มากรอกให้เองในป๊อปอัปของ QC**
- ผูกใบแล้ว → **ข้อค้างท้ายใบตามมาด้วย** พร้อมข้อความเดิม
- ผูกครบแล้วคิวต้องว่างและบอกว่าว่าง
