# 00 — สรุปสำหรับผู้บริหารและหัวหน้าแผนก

**อ่าน 5 นาที** · สำหรับใช้เปิดประชุมกับ SR / QC / LS / WH / AC

---

## 1. เรื่องนี้คืออะไร ในหนึ่งย่อหน้า

เราจะสร้างเว็บภายในหนึ่งหน้า ที่ทุกแผนกเข้ามาเห็นได้ว่า **ดีลแต่ละดีลไปถึงขั้นไหน ขาดเอกสารอะไร
และตอนนี้ค้างอยู่ที่ใคร** แต่ละแผนกอัพโหลดเอกสารของตัวเองเข้าไปที่เดียว ระบบแจ้งเตือนคนถัดไปเอง
โดยอัตโนมัติ **SAP ยังใช้เหมือนเดิมทุกอย่าง** — ระบบนี้ไม่ยุ่งกับการเปิด PO, เปิดรหัสสินค้า, ทำ GR
หรือการบันทึกบัญชี

---

## 2. ทำไมต้องทำ

ทุกวันนี้เอกสารหนึ่งชุดเดินทางผ่าน **5 เครื่องมือ**: Dochub (เซ็น) → Lark 3 กลุ่ม
(Internal Sourcing Team / Approval Request / QC FOOD) → LINE และ Email (คุยกับซัพ) →
ไดรฟ์ `M:\@Sourcing\2.0 Food\5.0 PO & Bank Swift\1.0 PO\2026 - PO Food` (เก็บไฟล์) →
ไปรษณีย์ (เอกสารตัวจริง)

ผลที่ตามมา:

| อาการ | ต้นเหตุ |
|---|---|
| ต้องถามในแชทว่า "PO ตัวนี้ไปถึงไหนแล้ว" | ไม่มีที่เดียวที่บอกสถานะ |
| **SR กลายเป็นบุรุษไปรษณีย์** | flow บังคับให้ SR ตามใบแจ้งหนี้จากซัพ, ส่งสลิปให้ซัพ, รับใบเสร็จตัวจริงแล้วเดินไปให้บัญชี |
| บัญชีปิดงานช้า | AC ต้องไล่ขอเอกสารเองก่อนทำ 3-way matching และไม่รู้ว่าขาดใบไหน |
| เอกสารตัวจริงหาย / ไม่รู้ถึงไหน | ส่งไปรษณีย์แล้วไม่มีใครบันทึกว่าใครรับ |
| งานตกหล่นเพราะข้อความไหลในกลุ่ม | แจ้งงานผ่านกลุ่มแชท ไม่ใช่คิวงานของแต่ละคน |
| สแกน/รวมไฟล์ซ้ำซ้อน | ไฟล์กระจายหลายที่ ต้องเอามารวมเองตอนปิดงาน |

**ประเด็นสำคัญ:** ปัญหาไม่ใช่ "ไม่มีระบบ" — เรามี SAP อยู่แล้ว ปัญหาคือ**ช่องว่างระหว่างแผนก**
ที่ SAP ไม่ได้ครอบ คือการส่งต่อเอกสารและการรู้สถานะ

---

## 3. ขอบเขต — สิ่งที่ระบบนี้ทำ และไม่ทำ

| ✅ ระบบนี้ทำ | ❌ ระบบนี้ไม่ทำ |
|---|---|
| เก็บเอกสารทุกใบของดีลไว้ที่เดียว | ไม่เปิด PO แทน SAP |
| แสดงสถานะและคนที่ค้างงาน | ไม่เปิดรหัสสินค้าแทน SAP |
| แจ้งเตือนอัตโนมัติเมื่อถึงคิว | ไม่ทำ GR แทน SAP |
| checklist บอกว่าขาดเอกสารใบไหน | ไม่บันทึกบัญชี / ไม่ออกงบ |
| อนุมัติ/เซ็นเอกสารในแอป | ไม่เก็บ stock / ไม่คำนวณต้นทุน |
| ติดตามเอกสารตัวจริงที่ส่งไปรษณีย์ | ไม่ทำจ่ายเงิน (AC ยังจ่ายทางเดิม) |
| บอก AC ว่าเอกสารพร้อมทำ 3-way matching หรือยัง | ไม่เก็บ line item ซ้ำกับ SAP |

**เลข PO จาก SAP เป็นตัวเชื่อม** ทุกอย่างในระบบนี้อ้างอิงเลข PO เดียวกับที่ใช้ใน SAP

---

## 4. ประโยชน์แยกตามแผนก

### Sourcing (SR) — ได้ประโยชน์มากที่สุด
- **หลุดจากบทบาทเดินเอกสาร** — AC อัพโหลดสลิปเอง WH อัพโหลด GR เอง ไม่ต้องรอ SR ส่งต่อ
- ไม่ต้องตามใบแจ้งหนี้ด้วยตัวเอง — ระบบเตือนตาม payment condition ใน PO ให้
- เซ็นอนุมัติที่เดียว ไม่ต้องสลับ Dochub + Lark 2 กลุ่ม
- ไม่ต้องตอบคำถาม "PO ตัวนี้ถึงไหน" อีก เพราะทุกคนเห็นเองได้

### QC
- เห็นคิวงานตรวจของตัวเองล่วงหน้า พร้อมวันที่นัดรับของ ไม่ต้องรอ SR แจ้งในกลุ่ม
- บันทึกผลตรวจ + แนบรูป ที่เดียว แทนการโพสต์ในกลุ่ม Lark-QC FOOD แล้วหาย
- กรณีไม่ผ่าน ระบบเปิดเรื่องเคลมและแจ้ง SR/AC ให้เอง — บัญชีจะไม่จ่ายเงินของที่ยังเคลมค้าง

### Logistics (LS)
- เห็นรายการที่ต้องจองรถล่วงหน้า พร้อมวันที่ ในหน้าเดียว
- งานเปิดรหัสสินค้าใหม่เข้าคิวให้ ไม่ต้องรอเอกสารเซ็นเดินมาถึงโต๊ะ

### Warehouse (WH)
- รู้ล่วงหน้าว่าของจะเข้าวันไหน PO ไหน ไม่ต้องรอ SR แจ้ง
- อัพโหลด GR เข้าระบบเอง จบหน้าที่ตัวเอง ไม่ต้องส่งต่อใคร

### Accounting (AC)
- **เลิกไล่ขอเอกสาร** — checklist บอกชัดว่าดีลไหนขาดใบไหน และเตือนเจ้าของเอกสารเองอัตโนมัติ
- ระบบบอกว่าดีลไหน "พร้อมบันทึก" แล้ว (มี PO + Invoice + GR ครบและยอดตรงกัน)
- ติดตามเอกสารตัวจริงได้ว่าอยู่ที่ใคร
- ปิดงานสิ้นเดือนเร็วขึ้น เพราะไม่ต้องรวมเอกสารเองตอนท้าย

### ผู้บริหาร / GM
- อนุมัติจากมือถือได้ ไม่ต้องเปิดหลายแอป
- เห็นภาพรวมว่างานค้างที่ขั้นตอนไหนมากที่สุด นานที่สุด ใครถือ

## 5. สิ่งที่แต่ละแผนกต้อง "เปลี่ยนพฤติกรรม"

พูดตรง ๆ ว่าระบบนี้จะได้ผลก็ต่อเมื่อมีการเปลี่ยนนิสัยการทำงาน ไม่ใช่แค่เพิ่มเว็บอีกตัว

| แผนก | ต้องเปลี่ยน | เลิกทำ |
|---|---|---|
| SR | สร้างดีลในระบบตอนเริ่มเช็คราคา + กรอกเลข PO จาก SAP | เลิกเป็นคนกลางส่งต่อเอกสารทุกใบ |
| QC | บันทึกผลตรวจในระบบ (แนบรูปได้) | เลิกแจ้งผลเฉพาะในกลุ่มแชท |
| LS | อัพเดตวันจองรถในระบบ | — |
| WH | อัพโหลด GR เข้าระบบทันทีหลังรับของ | เลิกรอ SR มาขอ |
| AC | อัพโหลดสลิป/Swift เข้าระบบเอง แล้วระบบแจ้งซัพให้ | เลิกส่งสลิปกลับให้ SR เพื่อให้ SR ส่งต่อ |
| ทุกแผนก | ถือว่าเอกสารในระบบคือฉบับจริง ไม่ใช่ที่อยู่ในแชท | เลิกเก็บไฟล์ส่วนตัวเป็นแหล่งอ้างอิง |

**ข้อที่ต้องตัดสินใจร่วมกัน:** จะยังใช้กลุ่ม Lark เดิมสำหรับแจ้งงานหรือไม่ ถ้าใช้ทั้งสองทางจะกลับไป
กระจายเหมือนเดิม ข้อเสนอคือ **ให้กลุ่ม Lark รับเฉพาะการแจ้งเตือนที่ระบบส่ง** และเลิกแจ้งงานด้วยมือ

## 6. สิ่งที่ต้องเตรียม

| เรื่อง | รายละเอียด |
|---|---|
| รายชื่อผู้ใช้ | ชื่อ อีเมล แผนก บทบาท และ Lark ID ของทุกคนที่เกี่ยวข้อง |
| สิทธิ์อนุมัติ | ใครเซ็นอะไร วงเงินเท่าไหร่ ลำดับไหน (ปัจจุบัน: SR Team → GM) |
| SLA ต่อขั้นตอน | แต่ละขั้นควรเสร็จในกี่ชั่วโมง/วัน — ให้หัวหน้าแผนกกำหนดเอง |
| Lark bot | สิทธิ์สร้าง bot/webhook เข้ากลุ่ม |
| Drive | โฟลเดอร์กลาง (แนะนำ Shared Drive) และการย้ายไฟล์เก่าจาก `M:` |
| ข้อกฎหมาย | ถ้าย้ายการเซ็นเข้าแอป ต้องให้ฝ่ายที่เกี่ยวข้องรับรองหลักฐาน e-signature (ดู [04](04-automation-approval.md) §5) |

## 7. แผนการทำงาน

| Phase | ได้อะไร | ใครเกี่ยวข้อง |
|---|---|---|
| **1 (ตอนนี้)** | เอกสารออกแบบ + flow ให้ทุกแผนกเห็นชอบ | ทุกแผนก — **ต้องการ feedback** |
| 2 | Google Sheet + โครงข้อมูล + flow งานซื้อในประเทศ | IT + SR |
| 3 | ใช้งานจริง: Deal Board, checklist, อัพโหลด | ทุกแผนก (ทดลอง 20 ดีลแรก) |
| 4 | ย้ายการอนุมัติเข้าแอป + Lark bot + เตือน SLA | SR + GM |
| 5 | 3-way readiness + dashboard คอขวด + งานนำเข้า | AC + ผู้บริหาร |

**ยังไม่เริ่มเขียนโปรแกรมโดยตั้งใจ** จนกว่า flow ในเอกสาร [01](01-flow-as-is-to-be.md) จะถูกต้องตามงานจริง
เพราะรอบก่อนออกแบบไปมากโดยยังไม่ทราบว่ามี SAP อยู่แล้ว จึงได้ระบบที่ซ้ำซ้อน — ไม่อยากให้เกิดซ้ำ

## 8. คำถามที่ต้องการคำตอบจากที่ประชุม

1. flow 17 ขั้นตอนใน [เอกสาร 01](01-flow-as-is-to-be.md) **ตรงกับงานจริงหรือไม่** มีขั้นที่ตกไปไหม
2. เอกสารบังคับของแต่ละดีลครบหรือไม่ (PI, PO, PO ที่ซัพเซ็นกลับ, Pattern label, ผลตรวจ QC, GR, Invoice, ใบลดหนี้, สลิป, ใบเสร็จตัวจริง)
3. SLA แต่ละขั้นควรเป็นเท่าไหร่
4. จะย้ายการเซ็นออกจาก Dochub จริงหรือไม่ หรือคงไว้สำหรับเอกสารที่ใช้กับภายนอก
5. จะเริ่มทดลองกับ **งานซื้อในประเทศ (อาหาร)** ก่อน แล้วค่อยขยายไปนำเข้า/Solar ใช่หรือไม่
6. ใครเป็นเจ้าของระบบ (ดูแลผู้ใช้ สิทธิ์ SLA) หลังใช้งานจริง
