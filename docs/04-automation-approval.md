# 04 — ระบบอัตโนมัติ แจ้งเตือน และการอนุมัติ

**เป้าหมาย:** ทุกการส่งต่องานข้ามแผนกเกิดขึ้นเองโดยไม่ต้องมีใครพิมพ์ข้อความบอกใคร

**หลักที่ยึด:** ระบบทำหน้าที่**ส่งต่อ** ไม่ใช่**ตัดสิน** — ระบบเปิดคิวงาน แจ้งเตือน และล็อกการจ่ายเงินได้
แต่จะไม่ตัดสินว่าสินค้าผ่าน QC หรือส่วนต่างราคายอมรับได้

## 2. การแจ้งเตือน

### ช่องทาง

| ช่อง | ใช้กับ | เหตุผล |
|---|---|---|
| **Lark bot (ข้อความส่วนตัว)** | คิวงานของแต่ละคน, ขออนุมัติ | ทีมใช้ Lark อยู่แล้ว เห็นเร็วกว่าอีเมล |
| **Lark กลุ่ม** | เรื่องที่ทั้งทีมควรรู้ (ผลตรวจไม่ผ่าน, เคลม) | แทนการโพสต์ด้วยมือในกลุ่มเดิม |
| **Email** | ขออนุมัติ (มีหลักฐาน), ส่งเอกสารให้ซัพ, สรุปรายวัน | แนบไฟล์ได้ ใช้กับคนภายนอกได้ |

> **✅ ตัดสินใจแล้ว: แจ้งเตือนภายในใช้ Lark อย่างเดียว — ไม่ทำ LINE**
> LINE เหลือไว้เฉพาะการติดต่อ**ผู้ขายภายนอก** ซึ่งอยู่นอกคิวแจ้งเตือนของระบบ
> `Notifications.channel` จึงมีค่าแค่ `LARK` / `EMAIL` / `WEB`
> ผลที่ตามมา: **ต้องมี `lark_user_id` ครบทุกคน** และต้องมีทางสำรองเมื่อ Lark ล่ม (ข้อ 7 ด้านล่าง)

### กติกาที่ทำให้ไม่กลายเป็นสแปม

ถ้าระบบเตือนมากเกินไป คนจะปิดการแจ้งเตือน แล้วระบบก็ไร้ประโยชน์ จึงมีกฎ:

1. **เข้าคิวก่อนส่งเสมอ** — ไม่ส่งทันทีตอนกดบันทึก (ถ้า Lark ล่ม งานผู้ใช้ต้องไม่ค้าง)
2. **กันส่งซ้ำ** — เรื่องเดียว คนเดียว วันเดียว ส่งครั้งเดียว (`dedupe_key`)
3. **ส่งซ้ำแบบถอยหลัง** — ถ้าส่งไม่สำเร็จ ลองใหม่ 5 นาที → 4 ชั่วโมง สูงสุด 5 ครั้ง
4. **ไม่มีงานค้าง = ไม่ส่งสรุป**
5. **เตือน SLA วันละครั้ง** ไม่ใช่ทุกชั่วโมง
6. **แจ้งคนที่ต้องลงมือเท่านั้น** — คนอื่นเข้ามาดูเองได้ในแอป
7. **Lark ส่งไม่ได้ → ตกไปที่อีเมลอัตโนมัติ** (จำเป็นเพราะไม่มีช่องทางที่สองแล้ว) —
   ครบ 5 ครั้งยังไม่สำเร็จให้ส่งเป็นอีเมลแล้วทำเครื่องหมาย `FALLBACK_EMAIL` ·
   ถ้าล้มเหลวเกิน 10 ข้อความใน 15 นาที ให้ขึ้นแบนเนอร์ในเว็บและแจ้งแอดมิน ·
   ผู้ใช้ที่ยังไม่มี `lark_user_id` ให้ส่งอีเมลแทนและขึ้นเตือนในหน้าตั้งค่า

### ตารางแจ้งเตือน

| เรื่อง | ถึงใคร | ช่อง |
|---|---|---|
| มีงานเข้าคิวคุณ | เจ้าของ stage | Lark ส่วนตัว |
| ขออนุมัติ | ผู้อนุมัติ (หรือผู้รับมอบอำนาจ) | Lark + Email |
| อนุมัติ / ไม่อนุมัติแล้ว | SR ผู้ดูแลดีล | Lark |
| **ผลตรวจ QC ไม่ผ่าน** | SR + QC Head + AC + WH | Lark กลุ่ม + Email |
| เปิดเรื่องเคลม | SR + AC | Lark + Email |
| ของจะเข้าคลังพรุ่งนี้ | WH | Lark กลุ่ม |
| ต้องจองรถ | LS | Lark |
| ใบแจ้งหนี้ครบกำหนดตาม condition | SR | Lark |
| เอกสารขาด | เจ้าของเอกสารใบนั้น | Lark |
| ดีลพร้อมบันทึกบัญชี | AC | Lark |
| จ่ายเงินแล้ว (แนบสลิป) | **ซัพพลายเออร์** | Email |
| เลย SLA | เจ้าของ → หัวหน้า | Lark + Email |
| สรุปงานรายวัน | ทุกคนที่มีงานค้าง | Email |

## 4. SLA และการวัดคอขวด

ทุกครั้งที่ stage เปลี่ยน ระบบบันทึกลง `Stage_Log` พร้อมจำนวนชั่วโมงที่ค้าง ทำให้คำนวณย้อนหลังได้เสมอ

**นิยามคอขวด:** stage ที่มีค่า `จำนวนงานค้าง × ชั่วโมงเฉลี่ยที่ค้าง` สูงสุด

```
┌─ งานค้างอยู่ที่ไหน (สัปดาห์นี้) ─────────────────────────┐
│ ขั้นตอน              ค้าง  เฉลี่ย  เลยกำหนด   คอขวด     │
│ ซัพเซ็น PO กลับ        7    38 ชม.     3      ███████ #1│
│ QC ตรวจรับ             4    22 ชม.     1      ████    #2│
│ อนุมัติภายใน           3    19 ชม.     1      ███     #3│
│ ใบเสร็จตัวจริง         5   120 ชม.     2      ██      #4│
└──────────────────────────────────────────────────────────┘
```

ตัวชี้วัดที่ได้ฟรีจาก `Stage_Log`: เวลาเฉลี่ยต่อขั้น · % งานเสร็จทัน SLA · เวลารวมตั้งแต่เช็คราคาถึงปิดบัญชี ·
% ที่ตรวจ 3-way ผ่านรอบแรก · จำนวนเคลมและมูลค่าแยกตามซัพ · ซัพที่ส่งเอกสารช้าที่สุด

**ประโยชน์ที่ได้ทันที:** ถ้าคอขวดอันดับ 1 คือ "ซัพเซ็น PO กลับ" นั่นแปลว่าปัญหาไม่ได้อยู่ในบริษัท
และควรไปคุยเรื่องเงื่อนไขกับซัพ ไม่ใช่กดดันทีมภายใน — ข้อมูลแบบนี้ตอนนี้ไม่มีใครรู้

## 5. การอนุมัติในแอป และหลักฐานทางกฎหมาย

ที่ประชุมเลือก **ย้ายการอนุมัติจาก Dochub + Lark เข้ามาในแอป** ทำได้ แต่มีเงื่อนไขที่ต้องทำให้ครบ

### สิ่งที่ระบบต้องเก็บทุกครั้งที่มีการกด "อนุมัติ"

| ข้อมูล | ทำไมต้องเก็บ |
|---|---|
| ตัวตนผู้อนุมัติ | ใช้ Google Workspace login — ไม่ใช่การพิมพ์ชื่อ |
| วันเวลาที่กด | ระบุเวลาที่ชัดเจน |
| **checksum ของไฟล์ที่อนุมัติ** | พิสูจน์ว่าเอกสารไม่ถูกเปลี่ยนหลังเซ็น — **ข้อนี้สำคัญที่สุด** |
| IP + อุปกรณ์ | ประกอบการยืนยันตัวตน |
| การกระทำก่อน/หลัง | อยู่ใน `Stage_Log` ที่เขียนเพิ่มเท่านั้น |
| ผู้รับมอบอำนาจ (ถ้ามี) | บันทึกว่าอนุมัติแทนใคร |

ทั้งหมดเก็บใน `Approvals` (คอลัมน์ `signed_file_checksum`, `signer_ip`, `user_agent`, `evidence_json`)

### ข้อควรระวัง — ต้องให้ผู้เกี่ยวข้องรับรองก่อนใช้จริง

พ.ร.บ. ว่าด้วยธุรกรรมทางอิเล็กทรอนิกส์รองรับลายมือชื่ออิเล็กทรอนิกส์ ถ้าสามารถ**ระบุตัวเจ้าของลายมือชื่อ**
และ**แสดงได้ว่าเจ้าของยอมรับข้อความนั้น** พร้อมมีวิธีตรวจสอบความน่าเชื่อถือ ปุ่ม "อนุมัติ" เฉย ๆ
ที่ไม่เก็บหลักฐานจึงไม่พอ ดีไซน์ข้างต้นออกแบบมาเพื่อข้อนี้

**ข้อเสนอ:** แบ่งเอกสารเป็น 2 กลุ่ม

| กลุ่ม | วิธีเซ็น | เหตุผล |
|---|---|---|
| **ภายใน** — ใบขออนุมัติเพิ่มรหัส, อนุมัติ PO ภายใน (SR Team → GM) | **ในแอป** | คู่กรณีคือคนในบริษัท ใช้หลักฐาน audit trail ได้ |
| **ภายนอก** — PO ที่ต้องให้ซัพเซ็นกลับ | **คง Dochub / เซ็นกระดาษ** | เป็นเอกสารผูกพันกับคู่ค้า ถ้ามีข้อพิพาทต้องใช้ในการเจรจา/ศาล |

แนวทางนี้ได้ประโยชน์เต็มที่ (ลด Dochub + Lark 2 กลุ่ม ในงานที่วนบ่อยที่สุด) โดยไม่รับความเสี่ยงกับเอกสารภายนอก
**ควรให้ผู้รับผิดชอบด้านกฎหมาย/บัญชีของบริษัทยืนยันก่อนเลิกใช้ Dochub สำหรับเอกสารกลุ่มใด**

### ขั้นตอนอนุมัติ

```
SR ส่งขออนุมัติ
   → SR Team (ตรวจ) ──ไม่ผ่าน→ ตีกลับ SR พร้อมเหตุผล
   → GM (อนุมัติ)   ──ไม่ผ่าน→ ตีกลับ SR พร้อมเหตุผล
   → เอกสารถูกล็อก (แก้ไม่ได้) + ไปขั้นต่อไป
```

- ผู้ขออนุมัติเอกสารตัวเองไม่ได้
- ถ้าอนุมัติแล้วมีการอัพโหลด version ใหม่ **การอนุมัติเป็นโมฆะและต้องอนุมัติใหม่** (นี่คือเหตุผลที่ต้องเก็บ checksum)
- ไม่อนุมัติต้องใส่เหตุผลทุกครั้ง
- ถ้าผู้อนุมัติลา ระบบส่งให้ผู้รับมอบอำนาจตาม `delegate_email` — ถ้าไม่มีระบบนี้ คนจะยืมรหัสกันใช้
