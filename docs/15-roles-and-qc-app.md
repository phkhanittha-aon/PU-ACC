# 15 — พนักงาน–ผู้จัดการ · ทุกยอดผ่านผู้จัดการ · เชื่อมกับแอปตรวจรับของ QC

สองเรื่องที่ทีมยืนยันกลับมา:

1. **แยกหน้าที่ = มีพนักงานและผู้จัดการ · ทุกยอดต้องผ่านผู้จัดการ** — ไม่มีเกณฑ์วงเงินให้ข้าม
   และหัวหน้าบัญชีต้องเป็นคนละคนกับคนบันทึกจ่าย
2. **QC มีแอปตรวจรับของตัวเองอยู่แล้ว** (Food และ Mech Incoming Inspection) — ระบบนี้ต้องไม่สร้างฟอร์มตรวจซ้ำ

---

## 1. บทบาทหลังแยก — 7 บทบาท

| บทบาท | คน | ถือขั้นตอนไหน | เห็นยอดเงิน | อนุมัติจ่าย |
|---|---|---|---|---|
| จัดซื้อ (SR) | คุณสมชาย | 6 ขั้น | ✓ | — (เป็นผู้ขอ) |
| QC | คุณสมหญิง | 2 ขั้น | — | — |
| โลจิสติกส์ (LS) | คุณอนุชา | 2 ขั้น | — | — |
| คลังสินค้า (WH) | คุณประเสริฐ | 1 ขั้น | — | — |
| **บัญชี (AC)** | คุณวิภา | 4 ขั้น · **เป็นผู้บันทึกการจ่าย** | ✓ | **ไม่ได้** |
| **หัวหน้าบัญชี (ACH)** | คุณอารีย์ | **ไม่ถือขั้นตอนใด** | ✓ | ✓ **ทุกยอด** |
| ผู้บริหาร (GM) | คุณผู้จัดการ | 2 ขั้น (ตัดสินใจซื้อ · อนุมัติ PO) | ✓ | — |

**หัวหน้าบัญชีไม่ถือขั้นตอนใดเลยโดยตั้งใจ** — หน้าที่คืออนุมัติอย่างเดียว
หน้าหลักของหัวหน้าบัญชีจึงมีแต่หมวด *⚑ รออนุมัติจ่ายจากคุณ* ไม่มีงานประจำวันมาปน

### สายอนุมัติ — ทุกยอดผ่านผู้จัดการ

```
พนักงานส่งคำขอ PRQ-26-xxxx
   │  (จัดซื้อ หรือ บัญชี ก็ได้ — ใครตั้งเรื่องก็ได้)
   ▼
ผู้จัดการฝ่ายบัญชี (คุณอารีย์) อนุมัติ  ◄── ทุกยอด ไม่มีเกณฑ์วงเงินให้ข้าม
   │
   ▼
บัญชี (คุณวิภา) บันทึกการจ่าย
```

**3 คน 3 หน้าที่ ไม่ทับกัน** — ผู้ขอ · ผู้อนุมัติ · ผู้บันทึกจ่าย

> **แก้จากรอบก่อน:** ผมเคยตั้งเป็นเกณฑ์วงเงิน (≤ ฿50,000 หัวหน้าบัญชี · เกินกว่านั้นผู้บริหาร)
> ซึ่ง**ผิด** — ทีมยืนยันว่าโครงสร้างคือ *พนักงานทำ ผู้จัดการอนุมัติ* และ **ทุกยอดต้องผ่านผู้จัดการ**
> เกณฑ์วงเงินถูกถอดออกจากสายอนุมัติทั้งหมดแล้ว
>
> ตัวเลข ฿50,000 ยังอยู่ที่เดียวคือ **เพดานซื้อเงินสดต่อรายการ** (`CASH_LIMIT`) ซึ่งเป็นคนละเรื่อง —
> เป็นกฎว่าเกินกว่านี้ต้องเปิด PO ไม่ใช่กฎว่าใครอนุมัติ

### กฎที่บังคับการแยกหน้าที่

| กฎ | เงื่อนไข | ผล |
|---|---|---|
| — | ผู้อนุมัติเป็นคนเดียวกับผู้ขอ | **บล็อก** ตอนกดอนุมัติ |
| **P13** *(ใหม่)* | ผู้บันทึกจ่ายเป็นคนเดียวกับผู้อนุมัติงวดนั้น | **บล็อก** ตอนบันทึกจ่าย |

P13 เช็คที่ **ชื่อคน** ไม่ใช่ที่บทบาท — ถ้าวันหนึ่งหัวหน้าบัญชีได้สิทธิ์บันทึกจ่ายด้วย
กฎนี้ยังกันไม่ให้เขาบันทึกจ่ายงวดที่ตัวเองอนุมัติ

### โครงสร้างเป็นข้อมูล ไม่ใช่เงื่อนไขในโค้ด

ทุกบทบาทมี 2 ช่อง: `lvl` (พนักงาน/ผู้จัดการ) และ `mgr` (ผู้จัดการของบทบาทนี้)
สายอนุมัติจ่ายชี้ที่ `PAY_APPROVER` ที่เดียว — **เปลี่ยนผู้อนุมัติ = แก้ค่าเดียว ไม่ต้องไล่แก้เงื่อนไขทั้งระบบ**

หน้าตั้งค่า → *ผู้ใช้และสิทธิ์* แสดงคู่พนักงาน–ผู้จัดการทั้งหมดในตารางเดียว

> **ที่ยังต้องยืนยัน:** ตอนนี้ให้ผู้จัดการฝ่ายบัญชีอนุมัติเรื่องเงินทุกใบ
> ถ้ายอดใหญ่ต้องมีลายเซ็นผู้บริหารเพิ่มอีกชั้น (สองลายเซ็น) บอกได้ — ระบบรองรับได้โดยเพิ่มขั้นอนุมัติที่สอง
> แต่ผมยังไม่ใส่ เพราะทีมบอกแค่ว่า *ทุกยอดต้องผ่านผู้จัดการ* ไม่ได้บอกว่ามีชั้นที่สอง

## 2. แอปตรวจรับของ QC ที่มีอยู่แล้ว

### สิ่งที่เปลี่ยนไปจากแผนเดิม

แผนเดิม (จาก [docs/14 §3.1](14-process-test-and-handoff.md)) ให้ QC กรอกผลตรวจในป๊อปอัปของระบบนี้
— **ผิด** เพราะ QC ตรวจในแอป Incoming Inspection ของตัวเองอยู่แล้ว การให้กรอกซ้ำคือเพิ่มงาน
และสร้างข้อมูลสองชุดที่ไม่ตรงกัน

**หลักที่ใช้แทน:**

> ระบบนี้เป็น Document Hub ไม่ใช่ระบบตรวจรับ — **ที่ไหนมีระบบอยู่แล้ว ให้ผูกไป ไม่ใช่ทำใหม่**
> เหมือนกับที่ไม่สร้าง PO ซ้ำเพราะ SAP B1 มีอยู่แล้ว

### QC ต้องทำอะไรบ้างในระบบนี้

ตรวจในแอปเดิมตามปกติ แล้วในระบบนี้กรอกแค่ 4 ช่อง:

| ช่อง | ทำไมต้องมี |
|---|---|
| **เลขที่ใบตรวจในแอป Incoming Inspection** | ตัวเชื่อมระหว่างสองระบบ · ผู้ตรวจสอบตามกลับไปหาใบเต็มได้ |
| อุณหภูมิที่วัดได้ | คลังใช้ตัดสินตอนรับเข้า · ขึ้นบนใบเคลมถ้าไม่ผ่าน |
| จำนวนที่ตรวจแล้วรับได้ | บัญชีใช้เทียบ 3 ทาง — **ตัวเลขที่ใช้จ่ายเงินจริง** |
| จำนวนที่ตีกลับ | ขึ้นบนใบเคลมที่ส่งให้ผู้ขาย · ใช้ตามใบลดหนี้ |

ป๊อปอัปของขั้น QC ขึ้นข้อความชัดว่า **“ตรวจในแอป Incoming Inspection ตามเดิม —
ระบบนี้ไม่มีฟอร์มตรวจซ้ำ”** เพื่อไม่ให้เข้าใจผิดว่าต้องตรวจสองที่

### 3 คำถามที่ต้องถามทีม QC ก่อนออกแบบการเชื่อมจริง

| # | คำถาม | ทำไมสำคัญ |
|---|---|---|
| 1 | แอปมี **API** หรือ **ส่งออกไฟล์** (CSV/JSON/Sheet) ได้ไหม | ตัดสินว่าจะดึงผลอัตโนมัติได้ หรือต้องให้ QC พิมพ์เลขใบตรวจเอง |
| 2 | ใบตรวจ**ผูกกับเลข PO อยู่แล้วหรือเปล่า** | ถ้าผูกอยู่แล้ว ระบบจับคู่ให้เองได้ ไม่ต้องกรอกเลขที่ใบตรวจเลย |
| 3 | ฟอร์ม **Food กับ Mech ใช้ช่องเดียวกันไหม** | Mech ไม่มีอุณหภูมิ · ถ้าช่องต่างกัน สัญญาของขั้น QC ต้องแยกตาม module |

**ระดับการเชื่อมที่เป็นไปได้ เรียงจากง่ายไปยาก**

| ระดับ | ทำอะไร | ต้องการอะไรจากแอป QC |
|---|---|---|
| 1 · ที่ทำไว้ตอนนี้ | QC พิมพ์เลขที่ใบตรวจ + สรุป 3 ตัว | ไม่ต้องแก้อะไรในแอป QC |
| 2 | ระบบดึงผลตามเลขที่ใบตรวจ QC ไม่ต้องพิมพ์สรุป | API อ่านใบตรวจตามเลขที่ |
| 3 | แอป QC ส่งผลมาเองเมื่อตรวจเสร็จ | webhook หรือ job ส่งออก |
| 4 | ฝังหน้าจอแอป QC ในหน้ารายละเอียด PO | แอปรองรับ iframe/ลิงก์ตรงตามเลขใบตรวจ |

**ยังไม่เลือกระดับ** — ต้องได้คำตอบ 3 ข้อข้างบนก่อน ตอนนี้ระบบทำระดับ 1 ไว้ซึ่งใช้งานได้ทันที
โดยไม่ต้องรอทีม QC แก้อะไร

## 3. เรื่องเดียวกันนี้กระทบส่วนอื่นตรงไหนบ้าง

| ส่วน | ผลกระทบ |
|---|---|
| **ตรวจ 3 ทาง** | ยังทำงานเหมือนเดิม เพราะ `จำนวนที่ QC รับได้` ยังเข้าระบบ แค่เปลี่ยนที่มา |
| **ใบเคลม** | ยังดึงอุณหภูมิและจำนวนที่ตีกลับจากที่ QC กรอกได้เหมือนเดิม · เพิ่มเลขที่ใบตรวจเป็นหลักฐานอ้างอิงให้ผู้ขาย |
| **การรวมไฟล์** | ผลตรวจฉบับเต็มอยู่ในแอป QC ไม่ใช่ในไดรฟ์กลาง — **ต้องตัดสินว่าจะดึงมาใส่ไฟล์รวมด้วยไหม** หรือใส่แค่เลขที่ใบตรวจอ้างอิง |
| **module Mech** | ถ้าฟอร์ม Mech ต่างจาก Food สัญญาของขั้น QC ต้องแยกตาม module — ซึ่ง `Stage_Templates` รองรับอยู่แล้ว (เพิ่มแถว ไม่ต้องแก้โค้ด) |

## 4. ทดสอบเรื่องนี้เอง

```bash
node tools/smoke.js     # 273 การเรนเดอร์ (7 บทบาท) + เคสแยกหน้าที่ + เคสแอป QC
```

เคสที่เพิ่ม:
- บัญชีตั้งเรื่องขอจ่ายแล้ว **ต้องไม่มีปุ่มอนุมัติให้ตัวเอง**
- **ยอดใหญ่ (฿122,500) ต้องไม่เด้งไปผู้บริหาร** — ไปที่ผู้จัดการฝ่ายบัญชีเหมือนยอดเล็ก
- ใบขออนุมัติ **ต้องไม่มีข้อความเรื่องเกณฑ์วงเงิน** เหลืออีกแล้ว
- หัวหน้าบัญชีเห็นปุ่มอนุมัติคำขอที่ส่งถึงตัวเอง และกดได้จริง
- ผู้อนุมัติ **บันทึกการจ่ายงวดที่ตัวเองอนุมัติไม่ได้** (P13)
- ป๊อปอัปขั้น QC บอกให้ไปตรวจในแอปเดิม และ**บังคับเลขที่ใบตรวจ**
- หน้าตั้งค่าแสดงทั้งสายงาน Food และ Mech พร้อมสถานะการเชื่อม
