# 19 · ต่อ Dashboard ตั้งเบิกทำจ่าย เข้ากับกระบวนการ Procure-to-Pay

> คำถามจากทีม: *"link กับ Procurement-to-pay"*

## สรุปคำตอบ

**Dashboard เป็นต้นทางของงวดจ่าย ไม่ใช่ที่อนุมัติ** — ไฟล์ Costing บอกว่า *ต้องจ่ายอะไรบ้าง*
ส่วนการแนบใบเรียกเก็บ ขออนุมัติ และบันทึกจ่าย ยังทำในระบบเอกสารตามสายเดิมทุกอย่าง

```
Costing Mech.xlsx           MGS Document Hub (P2P)
─────────────────           ────────────────────────────────────────
อัพเดท Dashboard
  │  ตัด LC · ตรวจ 4 ฟิลด์
  ▼
97 แถว 🟢 พร้อมทำจ่าย
  │
  │ กด "ส่งเข้า P2P"  ───────▶  เปิดเป็น "งวดจ่าย" ในรายการนั้น
  │                              │
  │                              ├─ จัดซื้อแนบเอกสารเรียกเก็บของงวดนั้น (PI / Invoice)
  │                              ├─ ส่งให้ผู้จัดการอนุมัติ  (ทุกยอด ไม่มีเกณฑ์วงเงิน)
  │                              └─ บัญชีบันทึกจ่าย  (คนละคนกับผู้อนุมัติ)
  │                              
  └─ จดลง Ledger ว่าส่งไปแล้ว ◀── รอบหน้าเอาไฟล์ใหม่ทับ แถวเดิมไม่ถูกส่งซ้ำ
```

**สิ่งที่ยากที่สุดไม่ใช่การส่ง แต่คือการไม่ส่งซ้ำ** — อ่านหัวข้อ 2

## 1. ทำไมต้องต่อ

ตอนนี้ข้อมูลสองฝั่งแยกกันอยู่

| ฝั่ง | รู้อะไร | ไม่รู้อะไร |
|---|---|---|
| ไฟล์ Costing | ต้องจ่ายใคร เท่าไหร่ เมื่อไหร่ ตามเงื่อนไขอะไร | ตั้งเบิกไปหรือยัง อนุมัติหรือยัง จ่ายไปแล้วหรือยัง |
| ระบบเอกสาร P2P | สถานะเอกสาร สายอนุมัติ ใครจ่าย จ่ายเมื่อไหร่ | ยอดที่ต้องจ่ายมาจากไหน มีอะไรที่ยังไม่ได้ตั้งเบิกบ้าง |

ผลคือมีคนต้องนั่งเทียบเองทุกเดือน ซึ่งเป็นงานที่คนทำพลาดได้และ**พลาดแล้วเป็นเรื่องเงิน**

## 2. เรื่องสำคัญที่สุด: กันตั้งเบิกซ้ำ

ไฟล์ Costing ถูก**เอาของใหม่ทับทุกรอบ** ถ้าไม่จดว่าแถวไหนส่งไปแล้ว
รอบหน้าแถวเดิมจะกลับมาเป็น `🟢 พร้อมทำจ่าย` อีกครั้ง แล้วถูกตั้งเบิกซ้ำ

### จดด้วยอะไร

**ไม่ใช่เลขแถว** — ไฟล์ใหม่เรียงไม่เหมือนเดิม แถวที่ 40 รอบนี้ไม่ใช่แถวที่ 40 รอบก่อน

ใช้ **ลายนิ้วมือแถว** แทน:

```
PO Number + รายการสินค้า + ยอด + วันครบกำหนด
```

ทั้งสี่อย่างรวมกันคือสิ่งที่ระบุ "งวดจ่ายหนึ่งงวด" ได้จริง และไม่เปลี่ยนตามลำดับแถวในไฟล์

> ตรวจแล้วกับไฟล์จริง: **97 แถว ได้ลายนิ้วมือ 97 อัน ไม่ชนกันเลย**
> `tools/costing-parity.mjs` ตรวจข้อนี้ทุกครั้งที่รัน — ชนเมื่อไหร่คือกันซ้ำไม่ได้จริง ต้องเพิ่มฟิลด์

### เก็บไว้ที่ไหน

ชีต **`Ledger`** ในไฟล์เดียวกัน

| ชีต | สร้างใหม่ทับได้ไหม |
|---|---|
| `Dashboard` | ได้ — สร้างใหม่ทุกครั้งที่กดอัพเดท ลบทิ้งก็ไม่มีอะไรหาย |
| `Log` | ได้ |
| **`Ledger`** | **ไม่ได้ — ห้ามลบ** ลบแล้วรายการเดิมจะถูกส่งซ้ำและตั้งเบิกซ้ำ |

คอลัมน์ในชีตนี้: ลายนิ้วมือแถว · PO · ผู้ขาย · ยอด · สกุลเงิน · วันครบกำหนด · ส่งเมื่อ · ส่งโดย · ผลการส่ง

หัวคอลัมน์ "ในระบบ P2P" บน Dashboard มีโน้ตเตือนเรื่องนี้ติดไว้แล้ว

## 3. ต่อได้ 3 ระดับ — เลือกได้ว่าจะไปถึงระดับไหน

| ระดับ | ทำอะไร | ต้องแก้อะไรในระบบเอกสาร | ใช้ได้เมื่อไหร่ |
|---|---|---|---|
| **1 · ลิงก์** | คอลัมน์ "ในระบบ P2P" กดแล้วเปิดรายการนั้นในระบบเอกสารทันที | **ไม่ต้อง** (ทำเสร็จแล้ว) | ทันที |
| **2 · จดสถานะ** | กด "ส่งเข้า P2P" แล้วจดลง `Ledger` · แถวที่ส่งแล้วไม่ถูกส่งซ้ำ | ไม่ต้อง | ทันที |
| **3 · ยิงข้อมูลจริง** | ส่งงวดจ่ายเข้าไปเปิดในระบบเอกสารเลย ไม่ต้องคีย์ | ต้องมีปลายทางรับ | เมื่อพร้อม |

**ระดับ 1 กับ 2 ใช้ได้เลยโดยไม่ต้องแก้อะไรในระบบเอกสาร** — และเป็นสองระดับที่กันเงินพลาดจริง
ระดับ 3 เป็นเรื่องความสะดวก ไม่ใช่เงื่อนไขว่าระบบจะเดินได้

### ระดับ 1 — ลิงก์ตรงถึงรายการ

ระบบเอกสารรับลิงก์แบบ `#po/<เลขรายการ>` แล้ว

```
https://…/prototype.html#po/PO-26-0060      → เปิดรายการนั้นเลย
https://…/prototype.html#po/PO-M226010001   → ไม่มีรายการนี้ ระบบค้นหาให้ + บอกว่าไม่พบ
```

**เจอเลขที่ยังไม่มีในระบบก็ไม่เงียบ** — เปิดหน้าค้นหาพร้อมเลขที่กรอกไว้ให้แล้ว
และขึ้นข้อความว่าไม่พบ ไม่ใช่โยนกลับหน้าแรกเฉย ๆ

ตั้งค่าใน Apps Script ที่ `CFG.HUB_URL` — ว่างไว้ก็ไม่ทำคอลัมน์ลิงก์ ไม่ error

### ระดับ 2 — ส่งเข้า P2P แล้วจดไว้

เมนู **ตั้งเบิกทำจ่าย → ส่งรายการที่พร้อมเข้าระบบ P2P**

- ส่งเฉพาะแถว `🟢` — แถว `🔴` ส่งไปปลายทางก็ตั้งเรื่องไม่ได้อยู่ดี **ปุ่มจึงไม่ขึ้นตั้งแต่แรก**
  ไม่ใช่ให้กดแล้วค่อยไปเด้ง error ที่ปลายทาง
- ถามยืนยันก่อน พร้อมบอกว่าจะส่งกี่รายการ กี่ใบ PO
- จดลง `Ledger` **ทีเดียวทั้งชุด** ไม่ใช่ทีละแถว — เขียนทีละแถวช้าและมีโอกาสค้างกลางทาง
- แถวที่ส่งแล้วขึ้นพื้นเขียวอ่อนบน Dashboard ว่าจบงานฝั่งนี้แล้ว

### ระดับ 3 — ยิงงวดจ่ายเข้าไปเลย

ตั้ง `CFG.HUB_ENDPOINT` แล้วระบบจะ POST ข้อมูลหนึ่งงวดต่อหนึ่งครั้ง

```json
{
  "source":    "COSTING_MECH",
  "ref":       "PO-M226010001|for KKE BESS project 2 units|1364|09.01.2026",
  "poNumber":  "PO-M226010001",
  "supplier":  "SUNGROW POWER SUPPLY CO.,LTD",
  "term":      "UNKNOWN",
  "amount":    1364,
  "currency":  "USD",
  "dueDate":   "09.01.2026",
  "item":      "for KKE BESS project 2 units",
  "zeroPrice": false,
  "sentAt":    "2026-08-27T10:22:31+07:00"
}
```

- `ref` คือลายนิ้วมือแถว — **ปลายทางใช้กันซ้ำอีกชั้นหนึ่ง** ไม่พึ่งฝั่งส่งอย่างเดียว
- ลงลายมือชื่อด้วยกุญแจลับร่วม (HMAC-SHA256) เก็บกุญแจใน Script Properties ไม่ใส่ไว้ในโค้ด
- ยิงไม่ผ่านก็**ยังจดใน `Ledger` พร้อมเหตุผล** — เพราะ Ledger คือสิ่งที่กันจ่ายซ้ำจริง ๆ
  ส่วนการยิงเป็นแค่ความสะดวก จดไว้แล้วคนไปเปิดงวดเองก็ได้

## 4. ต่อเข้าตรงไหนของกระบวนการ

งวดจ่ายที่ส่งเข้ามาไปโผล่ที่ **ขั้นทำจ่าย** ของรายการนั้น แล้วเดินตามสายเดิมทุกอย่าง

| ขั้น | ใคร | สิ่งที่ Costing ให้มาแล้ว | สิ่งที่ยังต้องทำในระบบเอกสาร |
|---|---|---|---|
| ตั้งงวดจ่าย | — | ยอด · สกุลเงิน · วันครบกำหนด · เงื่อนไข | — |
| แนบเอกสารเรียกเก็บ | จัดซื้อ | — | **แนบ PI / Invoice ของงวดนั้น** (บังคับ ดู [docs/16 §5](16-qc-report-mapping.md)) |
| ขออนุมัติ | จัดซื้อ | — | ส่งให้ผู้จัดการ — ทุกยอด ไม่มีเกณฑ์วงเงิน |
| อนุมัติ | หัวหน้าบัญชี | — | ต้องไม่ใช่ผู้ขอ |
| บันทึกจ่าย | บัญชี | — | ต้องไม่ใช่ผู้อนุมัติ |

**Costing ไม่ข้ามขั้นไหนเลย** — แค่ทำให้ไม่ต้องคีย์ยอดกับวันครบกำหนดซ้ำ และไม่มีงวดตกหล่น

## 5. ปัญหาการจับคู่เลข PO

เรื่องเดียวกับที่เจอตอนเชื่อมแอปตรวจรับ QC ([docs/17 §4](17-qc-app-integration.md))

| ที่มา | รูปแบบเลข | ตัวอย่าง |
|---|---|---|
| ไฟล์ Costing | `PO-M226xxxxxx` | `PO-M226010001` |
| ใบตรวจ QC ฝั่ง Mech | เลขรับของ `M-RCxxxxxxxx` | `M-RC26200090` |
| ใบรับสินค้าในใบตรวจ | `M-xxxxxxx` | `M-3026064` |
| ระบบเอกสาร (ตัวอย่าง) | `PO-26-xxxx` + DocNum ของ B1 | `PO-26-0060` / `10260` |

**สี่ชุดเลขสำหรับของล็อตเดียวกัน** ทางแก้เหมือนกัน — จับคู่อัตโนมัติเท่าที่ทำได้ ที่เหลือ**ไม่เดา**
แต่เข้าคิวให้คนจับคู่ แล้วจำการจับคู่นั้นไว้ใช้ครั้งหน้า

ระยะสั้นทำได้เลยคือ **ตารางเทียบเลข** หนึ่งชีต: `เลขในไฟล์ Costing ↔ เลขรายการในระบบเอกสาร`
เติมครั้งเดียวต่อ PO แล้วใช้ได้ตลอด

## 6. กรณีที่ต้องคิดไว้ก่อน

| กรณี | ระบบทำอะไร |
|---|---|
| **เอาไฟล์ใหม่ทับ แถวเดิมยังอยู่** | ลายนิ้วมือตรงกับ `Ledger` → ขึ้น "ส่งแล้ว" ไม่ส่งซ้ำ |
| **ยอดในไฟล์เปลี่ยน** (ต่อรองราคาใหม่) | ลายนิ้วมือเปลี่ยน → ถือเป็น**รายการใหม่** ต้องมีคนดูว่าจะยกเลิกงวดเดิมไหม |
| **แถวหายไปจากไฟล์รอบใหม่** | `Ledger` ยังจดไว้ · งวดที่ส่งไปแล้วไม่หายตามไฟล์ |
| **ส่งไปแล้วแต่ปลายทางไม่ได้รับ** | จดใน `Ledger` พร้อมเหตุผล ("ปลายทางตอบ 500" / "ส่งไม่ถึง") ตามเก็บได้ |
| **ลบชีต `Ledger` ทิ้ง** | ทุกแถวกลับเป็น "ยังไม่ส่ง" → **เสี่ยงตั้งเบิกซ้ำ** มีโน้ตเตือนบนหัวคอลัมน์ |
| **สองคนกดพร้อมกัน** | `LockService` กันไว้ คนที่สองได้ข้อความให้รอ |
| **แถวยอดศูนย์** | ส่งได้ (ข้อมูลครบจริง) แต่ส่ง `zeroPrice: true` ไปด้วยให้ปลายทางเตือนต่อ |

## 7. ทดสอบ

```bash
# ตรวจว่ากฎเดียวกันให้ผลตรงกันทั้งสองฝั่ง — สำคัญเพราะเขียนไว้สองที่
python3 tools/costing-extract.py "Costing Mech.xlsx" -o /tmp/py.json --grid /tmp/grid.json
node tools/costing-parity.mjs /tmp/grid.json /tmp/py.json
#   → ผลตรงกันทุกแถวระหว่าง Python กับ Apps Script (97 แถว) · ลายนิ้วมือไม่ชนกัน

python3 tools/costing-extract-test.py   # กฎการสกัดข้อมูลทุกข้อ
node tools/smoke.js                     # ระบบเอกสาร 287 การเรนเดอร์
```

`costing-parity.mjs` รันตัว `transform_` ของ Apps Script จริง ๆ บน Node โดยสตับเฉพาะสิ่งที่ Google ให้มา
แล้วเทียบผลทีละช่องกับฝั่ง Python — **ตอนเขียนครั้งแรกมันจับได้จริง** ว่าฝั่ง Python
ไม่ส่งค่า `incomplete` ออกมาเมื่อนับได้ 0 (ธรรมชาติของ `Counter`) ทำให้สองฝั่งเทียบกันไม่ได้ แก้แล้ว

ที่ทดสอบเพิ่มฝั่งระบบเอกสาร — ลิงก์ `#po/<เลข>` เปิดรายการที่มีจริงได้ ·
เลขที่ไม่มีในระบบต้องค้นหาให้และบอกว่าไม่พบ · เปลี่ยนลิงก์ระหว่างใช้งานแล้วหน้าเปลี่ยนตาม

ฝั่ง Dashboard ทดสอบบนเบราว์เซอร์จริง — กดส่งทีละแถวและส่งทั้งชุด · ตัวนับเปลี่ยนตาม ·
**รีโหลดแล้วยังจำว่าส่งไปแล้ว** (จำลองการเอาไฟล์ใหม่ทับ) · ล้างสถานะแล้วกลับเป็นยังไม่ส่งทั้งหมด

## 8. เรื่องที่ต้องตัดสินใจ

1. **ตารางเทียบเลข PO** — ใครเป็นคนดูแล และเติมตอนไหน (ตอนเปิด PO หรือตอนส่งเข้า P2P)
2. **ยอดเปลี่ยนหลังส่งไปแล้ว** — ให้ระบบเปิดงวดใหม่แล้วปล่อยงวดเดิมค้าง หรือบังคับให้คนไปยกเลิกก่อน
3. **UNKNOWN 5 แถว** — ส่งเข้า P2P ได้เลย หรือให้จัดซื้อไปเติมเงื่อนไขจริงก่อน
4. **หลายแถวต่อหนึ่ง PO** — 97 แถวมาจาก 49 ใบ · จะเปิดเป็นงวดจ่ายรายแถว หรือรวมเป็นงวดเดียวต่อใบ PO
   (Dashboard มีหน้าสรุปรายใบให้ดูแล้ว แต่ยังส่งเป็นรายแถว)
5. **ใครกดส่ง** — บัญชี จัดซื้อ หรือทั้งคู่ · ตอนนี้ใครเปิดสเปรดชีตได้ก็กดได้
