# 14 — ผลทดสอบทั้งกระบวนการ และ "สัญญาระหว่างขั้น" (Stage Contract)

รันจริงตั้งแต่ **ใบขอราคา → ใบเสนอราคา → PO → รับของ → ตั้งหนี้ → จ่าย → ปิดบัญชี**
สลับบทบาททุกแผนกตามลำดับจริง แล้วบันทึกว่า **แผนกที่รับงานต่อเห็นอะไรตอนเปิดหน้าจอครั้งแรก**

รันซ้ำได้เอง: `node tools/walkthrough.js` — จะพิมพ์ใบส่งงานของทั้ง 13 ทอดออกมา

---

## 1. ผลการทดสอบรอบแรก — เจอ 8 จุดที่ติดจริง

ทั้ง 8 จุดยืนยันจากการรันโค้ดจริง ไม่ใช่การอ่านเอกสารเดา

| # | จุดที่ติด | ผลกระทบต่อแผนกถัดไป | สถานะ |
|---|---|---|---|
| 1 | **QC ไม่เห็นสเปกที่ต้องใช้ตัดสิน** — สเปกอยู่แต่ในใบขอราคา ไม่เคยถูกคัดมาที่ PO | QC ตัดสินรับ/ไม่รับด้วยความจำ ถ้าคนตรวจเปลี่ยนคน เกณฑ์เปลี่ยนตาม | ✅ แก้แล้ว |
| 2 | **QC/คลัง ไม่รู้ว่าของจะมาถึงเมื่อไหร่** — LS จองรถแล้วบันทึกเป็นข้อความอิสระ | QC เตรียมคนไม่ทัน ต้องถามในไลน์ทุกครั้ง | ✅ แก้แล้ว |
| 3 | **คลังไม่เห็นผลตรวจของ QC** — ผลตรวจอยู่ในไฟล์แนบที่ต้องเลื่อนหา | คลังรับของเข้าทั้งล็อตทั้งที่ QC ตีกลับบางส่วน | ✅ แก้แล้ว |
| 4 | **บัญชีไม่รู้จำนวนที่ QC รับได้จริง** — ระบบเทียบแค่ยอดใบแจ้งหนี้กับยอด PO | จ่ายเต็มจำนวนทั้งที่ของไม่ครบ — ความเสียหายเป็นเงิน | ✅ แก้แล้ว |
| 5 | **ประวัติเขียนสิ่งที่ระบบไม่ได้ทำ** — `sappull` บันทึกว่า “สร้างงวดจ่ายจาก OCTG อัตโนมัติ” แต่โค้ดไม่ได้แตะเงื่อนไขจ่ายหรืองวดจ่ายเลย | PO ค้างเป็น *“รอกำหนดตอนผูกกับ B1”* ตลอดไป บัญชีไม่รู้ว่าต้องจ่ายวันไหน **และประวัติที่โกหกอันตรายกว่าไม่มีประวัติ** | ✅ แก้แล้ว |
| 6 | **ขั้น “ทำจ่าย” ปิดได้โดยไม่ต้องจ่าย** — เป็นปุ่ม *ทำ “ทำจ่าย” เสร็จ* ลอย ๆ ส่วนปุ่มบันทึกจ่ายจริงอยู่คนละที่ | PO เดินไปขั้นถัดไปโดยไม่มีสลิป ไม่มีเลขอ้างอิง | ✅ แก้แล้ว |
| 7 | **ปุ่มบอกว่า “งานจะไปที่บัญชี” ทั้งที่คนกดคือบัญชีเอง** | ผู้ใช้รอว่ามีคนมารับงานต่อ แต่จริง ๆ งานยังอยู่ที่ตัวเอง | ✅ แก้แล้ว |
| 8 | **ปุ่มไปที่ใบขอรหัสสินค้า พาไปหน้าเปล่า** — ไม่ได้เปิดใบให้ PO นั้น | LS เปิดไปเจอใบของ PO อื่น ต้องเดาว่าใบไหนของใคร | ✅ แก้แล้ว |

พบระหว่างทางอีก 2 จุดที่ไม่เกี่ยวกับการส่งต่อโดยตรง แต่แก้ไปด้วย:
ป๊อปอัปของรายการเก่าค้างบังรายการใหม่เมื่อสลับ PO · ชุดทดสอบพิมพ์ผลสรุปกลางไฟล์ทำให้เทสต์ท้ายไฟล์ไม่เคยถูกรายงาน

## 2. รากของปัญหา

ทั้ง 8 ข้อมีรากเดียวกัน ไม่ใช่บั๊กคนละเรื่อง:

> **ระบบรู้ว่า “ใครต้องทำอะไรต่อ” แต่ไม่รู้ว่า “ต้องส่งอะไรไปให้เขา”**

flow เดิมนิยามไว้แค่ 2 อย่างต่อขั้น — *ใครเป็นเจ้าของ* และ *SLA กี่ชั่วโมง*
สิ่งที่ขาดคืออย่างที่สาม: **ขั้นนี้ต้องส่งมอบข้อมูลอะไรให้ขั้นถัดไป**

ตราบใดที่ไม่มีข้อนี้ ความรู้จะอยู่ในหัวคนและในแชท — เปลี่ยนคนเมื่อไหร่ ความรู้หายทันที
และไม่มีใครรู้ว่ามันหายจนกว่าจะเกิดความเสียหาย

## 3. คอนเซ็ปต์ที่ใช้แก้: สัญญาระหว่างขั้น (Stage Contract)

**หลักการ:** ทุกขั้นต้องประกาศเป็นข้อมูล (ไม่ใช่เป็นโค้ด ไม่ใช่ความจำ) ว่า

1. ขั้นนี้ **ต้องกรอกอะไร** ก่อนส่งต่อ
2. **ใครเอาไปใช้** (บอกคนกรอกว่ากรอกให้ใคร ไม่ใช่กรอกให้ระบบ)
3. ขั้นนี้ **ต้องใช้อะไร** จากขั้นก่อนหน้า

จากนั้นระบบสร้างพฤติกรรม 4 อย่างขึ้นมาเองจากตารางเดียวกัน:

| กลไก | ทำอะไร |
|---|---|
| **ป๊อปอัปถามเฉพาะสิ่งที่ปลายทางต้องใช้** | ขั้นจองรถถามวันเวลาที่ของถึง · ขั้น QC ถามอุณหภูมิและจำนวนที่รับได้ · ขั้นคลังถามจำนวนที่รับเข้าจริง — ไม่ใช่ช่องหมายเหตุอิสระที่ใครเขียนตามใจ |
| **ใบส่งงาน** | หน้าจอของแผนกถัดไปขึ้นกล่อง *“แผนกก่อนหน้าส่งอะไรมาให้คุณ”* **เหนือปุ่มที่ต้องกด** ไม่ต้องเลื่อนหา ไม่ต้องเปิดไฟล์แนบ |
| **บล็อกตอนส่งต่อ** | ไม่กรอกสิ่งที่ปลายทางต้องใช้ = ส่งต่อไม่ได้ พร้อมข้อความว่า *“บัญชีต้องใช้ข้อมูลนี้ ไม่งั้นเขาต้องโทรถามคุณ”* |
| **เตือน + ถามกลับ 1 คลิก** | ถ้าข้อมูลที่ขั้นนี้ต้องใช้หายไป (เช่นข้อมูลเก่าก่อนขึ้นระบบ) ขึ้นแถบแดงบอกว่าขาดช่องไหน จากแผนกไหน พร้อมปุ่มถามกลับที่ส่ง Lark ให้เอง |

**เพิ่มช่องใหม่ = เพิ่มบรรทัดในตาราง ไม่ต้องแก้หน้าจอ** — หลักการเดียวกับที่ใช้กับ `Stage_Templates`

### 3.1 สัญญาที่ตั้งไว้ตอนนี้

| ขั้น | แผนก | ต้องส่งมอบ | ใครใช้ต่อ |
|---|---|---|---|
| ผู้ขายเซ็น PO กลับ | จัดซื้อ | ผู้ขายนัดส่งของวันที่ | โลจิสติกส์ |
| จองรถรับของ | โลจิสติกส์ | ของถึงห้องเย็นวันที่ · เวลา · ทะเบียนรถ | QC และคลัง |
| QC ตรวจรับ | QC | อุณหภูมิที่วัดได้ · **จำนวนที่รับได้** · จำนวนที่ตีกลับ | คลังและบัญชี |
| รับเข้าคลัง + GR | คลัง | **จำนวนที่รับเข้าจริง** · เลข GRPO ใน B1 | บัญชี |
| รับใบแจ้งหนี้ | บัญชี | เลขใบแจ้งหนี้ของผู้ขาย · ยอดในใบแจ้งหนี้ | จัดซื้อและบัญชี |
| ใบเสร็จตัวจริง | บัญชี | ใครเป็นผู้รับเอกสารตัวจริง | บัญชี |

### 3.2 ตัวอย่างจริงจากการรัน

หน้าจอ **คลังสินค้า** ตอนรับงานต่อจาก QC (พิมพ์จาก `tools/walkthrough.js`):

```
แผนกก่อนหน้าส่งอะไรมาให้คุณ
  QC · QC ตรวจรับ
     อุณหภูมิที่วัดได้ (°C)      -18.7
     จำนวนที่ตรวจแล้วรับได้      300 KG
     จำนวนที่ตีกลับ (ถ้ามี)      —
  LS โลจิสติกส์ · จองรถรับของ
     ของถึงห้องเย็นวันที่        06/09/2026
     เวลาโดยประมาณ              08:00
     ทะเบียนรถ / ผู้ขนส่ง        70-5566 กทม
```

เดิมหน้าจอนี้มีแค่ *“งานนี้อยู่ที่คุณ — รับเข้าคลัง + GR”* แล้วให้คลังไปหาเอาเองว่าของอะไร มาถึงเมื่อไหร่ QC ว่ายังไง

## 4. ผลที่ตามมาจากคอนเซ็ปต์นี้

### 4.1 ตรวจ 3 ทางกลายเป็นของจริง

เดิมเทียบแค่ **ยอดใบแจ้งหนี้ กับ ยอด PO** — ซึ่งไม่ใช่การตรวจ 3 ทาง
ตอนนี้มี `จำนวนที่ QC รับได้` และ `จำนวนที่คลังรับเข้า` เป็นข้อมูลจริงแล้ว ระบบจึงเทียบได้ว่า

- QC รับได้ 80 KG แต่คลังรับเข้า 120 KG → **บล็อกการปิดบัญชี**
- ยังไม่มีจำนวนจาก QC หรือคลัง → เตือนว่า *เทียบ 3 ทางไม่ได้* พร้อมบอกว่าต้องไปเอาจากแผนกไหน

นี่คือกฎที่ [docs/09](09-usability-and-sap.md) เขียนไว้ว่าต้องเทียบกับ **จำนวนที่ QC รับ ไม่ใช่จำนวนที่ส่งมา**
— ก่อนหน้านี้เขียนไว้แต่ทำไม่ได้ เพราะไม่มีข้อมูล

### 4.2 ประวัติต้องตรงกับสิ่งที่ระบบทำจริง

ข้อ 5 ในตารางแรกน่ากลัวที่สุดในบรรดาที่เจอ เพราะระบบ **เขียนในประวัติว่าทำสิ่งที่ไม่ได้ทำ**
คนอ่านประวัติแล้วเชื่อ แล้วไม่ไปตรวจซ้ำ

ตอนนี้ `sappull` อ่านเงื่อนไขชำระ ตั้งค่า `เครดิต 30 วัน` และ **สร้างงวดจ่ายพร้อมวันครบกำหนดจริง**
แล้วจึงเขียนประวัติตามสิ่งที่ทำ — ถ้าเงื่อนไขตรงอยู่แล้วก็เขียนว่าไม่ได้เปลี่ยนอะไร

> **กติกาที่ควรถือต่อไป:** ห้ามเขียนประวัติสิ่งที่โค้ดไม่ได้ทำจริง แม้จะตั้งใจทำในอนาคต

### 4.3 ขั้นตอนที่ต้องมี "ผลลัพธ์" ห้ามปิดด้วยปุ่มเปล่า

ขั้นทำจ่ายไม่มีปุ่ม *เสร็จ* อีกแล้ว — มีแต่ปุ่มพาไปยังงวดที่ต้องจ่าย
ปุ่มปิดขั้นจะโผล่ก็ต่อเมื่อ **จ่ายครบทุกงวดจริง**

หลักการเดียวกันใช้ได้กับขั้นอื่นที่มีผลลัพธ์วัดได้ เช่น ขั้นเปิดรหัสสินค้า (ต้องได้รหัสจาก B1 จริง)

## 5. สิ่งที่ยังไม่ได้ทำ และต้องให้ทีมตัดสิน

| # | เรื่อง | ทำไมยังไม่ทำ |
|---|---|---|
| 1 | **สัญญาของขั้นที่เหลืออีก 11 ขั้น** ยังไม่ได้กำหนด (คอนเฟิร์มออเดอร์ · รับ PI · อนุมัติภายใน ฯลฯ) | ต้องให้เจ้าของขั้นบอกเองว่าแผนกถัดไปต้องใช้อะไร — ถ้าผมเดาให้ จะกลายเป็นช่องบังคับที่ไม่มีใครใช้ |
| 2 | **จำนวนยังเป็นข้อความ** (`300 KG`) ไม่ใช่ตัวเลข + หน่วย | ระบบจึงเทียบได้แค่ “ตรงกันไหม” ยังคำนวณส่วนต่างไม่ได้ · ต้องรู้ก่อนว่าหน่วยจริงมีกี่แบบ |
| 3 | **ยังไม่บล็อกเมื่อคลังรับเข้ามากกว่าที่ QC รับได้** ตอนคลังกรอก | ตอนนี้เตือนตอนบัญชีปิด ซึ่งช้าไป 2 ขั้น — แต่ต้องรู้ก่อนว่ามีเคสที่รับเกินโดยชอบธรรมไหม |
| 4 | **ข้อมูลเก่าก่อนขึ้นระบบไม่มีสัญญาเหล่านี้** | ระบบจะขึ้นแถบแดง “ถามกลับ” เต็มไปหมดในเดือนแรก · ต้องตัดสินว่าจะเติมย้อนหลัง หรือปิดการเตือนสำหรับ PO ที่เปิดก่อนวันขึ้นระบบ |

**คำถามที่อยากให้แต่ละแผนกตอบ** — เอาไปถามในที่ประชุมได้เลย:

> *“เวลาคุณรับงานต่อจากแผนกก่อนหน้า มีอะไรที่คุณต้องเดินไปถามหรือทักไลน์ถามเกือบทุกครั้ง?”*

คำตอบของคำถามนี้คือรายการช่องที่ต้องเพิ่มเข้าไปในตารางสัญญา — ไม่ต้องออกแบบหน้าจอใหม่

## 6. วิธีรันทดสอบเอง

```bash
node tools/walkthrough.js   # เดินทั้งกระบวนการ พิมพ์ใบส่งงานของทั้ง 13 ทอด
node tools/smoke.js         # ชุดทดสอบ 234 การเรนเดอร์ + เคสของทุกฟีเจอร์
```

ทั้งสองสคริปต์อ่าน `presentation/prototype.html` โดยตรงและรันบน DOM ปลอม
ไม่ต้องติดตั้งอะไรเพิ่ม ไม่ต้องเปิดเบราว์เซอร์
