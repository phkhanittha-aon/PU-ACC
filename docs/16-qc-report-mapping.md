## 2. ปัญหาที่ใหญ่ที่สุดที่เจอ — "ใบผ่าน แต่ยังไม่จบ"

ใบ F-2026049 สรุปผลว่า **Pass ทุกช่อง** แต่ตาราง Defect & Remark ท้ายใบเขียนไว้ว่า

| ข้อบกพร่องที่พบ | หมายเหตุ |
|---|---|
| พบกล่องบุบ เสียรูป และมีร่องรอยความชื้น | **รอสรุปเรื่องเปลี่ยนกล่อง** |
| พบขนาดกล่องไม่เท่ากัน | พี่จอจะให้ Sale ขายกล่องต่าง Size ต่างราคา **รอสรุป** |

**ผลรวมของใบคือผ่าน → ระบบเดินต่อ → บัญชีจ่ายเต็มจำนวน**
ทั้งที่เรื่องเปลี่ยนกล่องกับผู้ขายยังไม่จบ และยังไม่รู้ว่าจะได้ส่วนลดหรือของชดเชยหรือไม่

นี่คือ**ช่องโหว่ที่เงินไหลออกก่อนเรื่องจบ** และไม่มีใครผิด — เพราะข้อมูลนั้นอยู่หน้าที่ 23 ของ PDF
ที่ไม่มีใครนอกจาก QC เปิด

### วิธีแก้: ข้อค้างจากใบตรวจ (QC Open Item)

ทุกบรรทัดใน Defect & Remark ที่ยังไม่จบ ถูกยกออกมาเป็น **"ข้อค้าง"** ผูกกับรายการ แยกเป็น 2 ชั้น

| ชั้น | ผลต่อระบบ |
|---|---|
| **ข้อค้างที่ต้องสรุปก่อนจ่ายเงิน** | **ล็อกงวดจ่ายทันที** (สถานะ BLOCKED) · ตั้งเรื่องขออนุมัติจ่ายไม่ได้ · แจ้งจัดซื้ออัตโนมัติ |
| ข้อค้างที่ไม่กระทบการจ่าย | ขึ้นเตือนบนหน้าจอปลายทางและใน "ตรวจสอบก่อนบันทึก" แต่ไม่ล็อกเงิน |

**การปิดข้อค้างต้องเขียนว่าสรุปว่าอย่างไร** — กดปิดเฉย ๆ ไม่ได้
ปิดครบเมื่อไหร่ ระบบ**ปลดล็อกงวดจ่ายให้เอง**และแจ้งบัญชี
ข้อความที่สรุปไว้เข้าไปอยู่ในชุดเอกสารรวมเล่มตอนปิดรายการ

> ใครปิดได้: จัดซื้อ (คนคุยกับผู้ขาย) · QC (เรื่องคุณภาพ) · ผู้จัดการ
> ใบลดหนี้อย่างเดียวไม่ปลดล็อกให้ ถ้ายังมีข้อค้างที่ล็อกไว้ค้างอยู่

## 3. ช่องที่ระบบขอจากใบตรวจ — ขอเท่าที่ปลายทางใช้

ระบบนี้ **ไม่ทำฟอร์มตรวจซ้ำ** QC ยังตรวจในแอป Incoming Inspection เดิม
สิ่งที่ขอมาคือ "หัวใบ + สรุปผล" ที่แผนกถัดไปต้องใช้ตัดสินใจ

### ช่องกลาง (ทั้งสองสาย)

| ช่อง | ตรงกับใบตรวจ | ปลายทางเอาไปทำอะไร |
|---|---|---|
| `qcRef` | Report No. | เลขอ้างอิงในชุดเอกสารและใบขออนุมัติจ่าย |
| `qcPoRef` | PO Ref No. | จับคู่กับรายการ — **ต่างจากเลขในระบบเมื่อไหร่ ระบบเตือนทันที** |
| `qcDate` | Inspection Date | วันตรวจจริง ไม่ใช่วันออกใบ |
| `qcPlace` | Location | คลังต้องรู้ว่าของอยู่ห้องเย็นใครก่อนไปรับ |
| `invQty` | INV QTY | เทียบกับ Actual QTY และยอดในใบแจ้งหนี้ |
| `qtyOk` | Actual QTY | **ตัวตั้งของการตรวจ 3 ทาง** |
| `qcResult` | Result | ไม่ผ่าน = เปิดใบเคลม |
| `qtyBad` | (จากส่วนที่ตีกลับ) | ขึ้นบนใบเคลมที่ส่งผู้ขาย · บังคับกรอกเมื่อผลไม่ผ่าน |

### ช่องเฉพาะสาย

| สาย | ช่องเพิ่ม | เหตุผล |
|---|---|---|
| **FOOD** | `temp` · `lot` · `expDate` · `grade` | ตารางล็อตและ Temp. มีเฉพาะใบอาหาร · คลังใช้จัดเก็บ ฝ่ายขายใช้ตั้งราคาตามเกรด |
| **MECH** | `conCond` | ใบเครื่องจักรตรวจสภาพตู้/หีบห่อแทนอุณหภูมิ |

โครงในโค้ด — เพิ่มสายใหม่ = เพิ่มแถว ไม่ต้องแก้หน้าจอ

```js
QC_INCOMING: {
  to:"คลังสินค้า และบัญชี", app:"QCAPP",
  f:[ /* ช่องกลาง */ ],
  byMod:{ FOOD:[temp, lot, expDate, grade], MECH:[conCond] }
}
```

## 4. การเทียบจำนวนแบบรู้หน่วย

ของเดิมเทียบด้วย `String(a) === String(b)` → พังทันทีที่หน่วยเข้ามา

ตอนนี้แยกเป็น **ตัวเลข + หน่วย** แล้วเทียบทีละส่วน (`CTNs`/`cartons`/`กล่อง` → `ctn`, `KGS`/`กก.` → `kg`)

| กรณี | ผลที่ระบบบอก |
|---|---|
| `2,600 CTNs` กับ `2600 CTN` | ✓ ตรงกัน |
| `2,600 CTNs` กับ `2600 KG` | **!** เลขตรงแต่หน่วยไม่ตรง — ให้ใช้หน่วยเดียวกัน (เตือน ไม่บล็อก) |
| `2,600 CTNs` กับ `2,540 CTNs` | **✕** จำนวนไม่ตรง — ต้องแก้ก่อนตั้งหนี้ (บล็อก) |

เพิ่มการเทียบใหม่ด้วย: **INV QTY เทียบกับ Actual QTY** — ใบตรวจทำไว้แล้วในตัวเอง
ระบบยกผลนั้นมาให้บัญชีเห็น แทนที่จะให้บัญชีเปิด PDF ไปนับเอง

## 5. เอกสารเรียกเก็บ "รายงวด" — งวดที่ 1 กับงวดที่ 2 คนละใบ

### ปัญหาเดิม

คำขออนุมัติจ่ายแนบเอกสาร**ของทั้ง PO รวม ๆ** ผู้อนุมัติจึงไม่มีทางรู้ว่า
**งวดนี้เรียกเก็บด้วยใบไหน** และไม่มีอะไรกันไม่ให้ใช้ใบแจ้งหนี้ใบเดิมขอจ่ายซ้ำ

### ตอนนี้

ทุกงวดต้องผูก **เอกสารเรียกเก็บของงวดนั้นเอง** ก่อนส่งขออนุมัติ

| ช่อง | บังคับ | หมายเหตุ |
|---|---|---|
| ประเภทเอกสาร | ✓ | **PI / ใบเรียกเก็บมัดจำ** · **ใบแจ้งหนี้ตัวจริง** · **ใบวางบิล / Debit Note** |
| เลขที่เอกสาร | ✓ | ผู้อนุมัติต้องรู้ว่าจ่ายตามใบไหน |
| ยอดตามเอกสาร | ✓ | ใช้เทียบกับยอดที่ขอจ่าย |
| ไฟล์เอกสาร | ✓ | เข้าไดรฟ์กลางชื่อ `<เลขรายการ>_BILL_<งวด>.pdf` อัตโนมัติ |

ระบบเดาประเภทให้ตามชนิดงวด — งวด**มัดจำ**เดาเป็น **PI** (ตอนมัดจำยังไม่มีใบแจ้งหนี้ตัวจริงเพราะของยังไม่ส่ง)
งวดที่เหลือเดาเป็น **ใบแจ้งหนี้ตัวจริง**

### กฎที่ระบบบังคับ

| รหัส | กฎ |
|---|---|
| S8 | ต้องระบุเลขที่เอกสารเรียกเก็บของงวดนี้ |
| S9 | ต้องแนบไฟล์เอกสารเรียกเก็บ — **คำขอที่ไม่มีใบเรียกเก็บไม่ควรมีใครกดอนุมัติ** |
| S10 | ต้องระบุยอดตามเอกสาร |
| S11 | ขอจ่ายเกินยอดในเอกสารเรียกเก็บไม่ได้ |
| **S12** | **ใบเดิมถูกใช้ขอจ่ายงวดอื่นไปแล้ว และรวมกันเกินยอดในใบ → บล็อก (กันจ่ายซ้ำ)** |
| S13 | เลือก "ใบแจ้งหนี้ตัวจริง" ทั้งที่ยังไม่ถึงขั้นรับใบแจ้งหนี้ → เตือนให้ใช้ PI |

S12 คือกฎที่กันเคสคลาสสิก: ผู้ขายวางบิลใบเดียว แล้วมีคนขอจ่ายสองรอบด้วยใบเดียวกัน
ระบบยอมให้ใบเดียวกันครอบหลายงวดได้ (เช่นแบ่งจ่าย 2 รอบตามใบเดียว) **แต่รวมกันต้องไม่เกินยอดในใบ**

### หน้าจอ

- ป๊อปอัปขออนุมัติจ่ายมี **แถบเลือกงวด** อยู่บนสุด เห็นทุกงวดของรายการนั้นพร้อมกัน
  ว่างวดไหนสถานะอะไร ใช้เอกสารเรียกเก็บใบไหน
- กดงวดที่**ตั้งเรื่องหรือจ่ายไปแล้ว** → เปิดแบบ**ดูอย่างเดียว** เห็นว่าใช้ใบไหนตอนนั้น แต่แก้ไม่ได้
- ตารางงวดจ่ายเพิ่มคอลัมน์ **"เอกสารเรียกเก็บ"** — งวดที่ยังไม่แนบขึ้นป้าย **ยังไม่แนบ**
- **ใบขออนุมัติ**ขึ้นหัวข้อ *"งวดนี้เรียกเก็บด้วยเอกสารใบไหน"* เป็นบล็อกแรกก่อนรายการเอกสารอื่น
  ถ้ายอดในใบมากกว่ายอดที่ขอ ระบบเขียนให้เลยว่า "ที่เหลือเรียกเก็บงวดถัดไป"
- ชุดเอกสารรวมเล่มตอนปิดรายการ เรียง **ใบเรียกเก็บงวดที่ N → สลิปงวดที่ N** คู่กัน ตรวจย้อนหลังทีละงวดได้

### เก็บของเดิมไว้ด้วย

บัญชีตั้งเรื่องขอจ่ายเองจากตารางงวด (ปุ่ม *ตั้งเรื่องขอจ่าย*) **ใช้ฟอร์มเดียวกัน** —
เดิมกดแล้วเปลี่ยนสถานะทันทีโดยไม่มีเอกสารผูก ตอนนี้ต้องแนบเหมือนกัน
และการตั้งเรื่องจากตารางงวด**ไม่เดินขั้นตอนของรายการ** (เพราะไม่ใช่การจบขั้น "ส่งมอบเอกสาร")

## 7. คำถามที่ยังต้องถามทีม QC / จัดซื้อ

1. **แอป Incoming Inspection ส่งข้อมูลออกได้ทางไหน** — API? ส่งออก Excel/CSV? หรือให้กรอกเลขใบเอาไปก่อน
2. **ฝั่ง Mech จะจับคู่ใบตรวจกับ PO ด้วยอะไร** — ในเมื่อ PO Ref No. บนใบเป็นเลขรับของ
   (`M-RC26200090` กับ `M-3026064` เป็นคนละชุด) ต้องมีตารางเทียบหรือให้เลือกจากรายการ
3. **Sampling plan (General II / Normal plan)** ต้องเก็บเข้าระบบด้วยไหม — ตอนนี้ยังไม่เก็บ
   ถ้าผู้ตรวจสอบภายนอกขอดู จะต้องเปิด PDF เอง
4. **Data Logger** ของใบอาหาร — เก็บแค่ Yes/No หรือแนบกราฟด้วย
5. **ลายเซ็นสองคน** (QC + ผู้จัดการจัดซื้อ) — ระบบควรบล็อกไม่ให้ส่งต่อจนกว่าจะมีลายเซ็นครบไหม
   ตอนนี้ยังไม่บล็อก บล็อกแค่ว่าต้องแนบไฟล์ใบตรวจ
6. **ใบฝากสินค้าห้องเย็น (Ruxchai Deposit Form)** ที่แนบท้ายใบอาหาร — เป็นเอกสารบังคับของชุดหรือไม่
   ตอนนี้ยังไม่ได้อยู่ในรายการเอกสารบังคับ

## 8. ทดสอบแล้ว

```
node tools/smoke.js       # 280 เรนเดอร์ + เคสใหม่ทั้งหมด → ผ่าน
node tools/walkthrough.js # เดินครบ 13 ขั้น ปิดรายการได้
```

เคสใหม่ที่เพิ่มในชุดทดสอบ

- ป๊อปอัป QC ฝั่ง **Mech ต้องไม่มี**ช่องอุณหภูมิและช่องเลขล็อต แต่**ต้องมี**ช่องสภาพตู้
- ป๊อปอัป QC ฝั่ง **Food ต้องมี**ช่องเกรด
- คลังเห็นเลขที่ใบตรวจและสถานที่ตรวจโดยไม่ต้องเปิด PDF
- เลข PO Ref บนใบตรวจไม่ตรงกับรายการ → ระบบต้องเตือน
- ใบตรวจผ่านแต่มีข้อค้าง → **ล็อกจ่าย** และตั้งเรื่องขอจ่ายไม่ได้
- ปิดข้อค้างโดยไม่เขียนว่าสรุปอย่างไร → **ไม่ให้ปิด**
- ปิดข้อค้างครบ → **ปลดล็อกงวดจ่ายเอง**
- ไม่แนบเอกสารเรียกเก็บของงวด → บล็อก (S9) · ไม่ใส่เลขที่ → บล็อก (S8)
- ขอจ่ายเกินยอดในใบเรียกเก็บ → บล็อก (S11)
- ใช้ใบเรียกเก็บใบเดิมขอจ่ายซ้ำจนเกินยอดในใบ → บล็อก (S12)
- สลับดูงวดที่จ่ายไปแล้ว → เห็นใบที่ใช้ตอนนั้น แต่ไม่มีปุ่มส่งขออนุมัติ
