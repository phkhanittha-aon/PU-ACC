# 16 — ระบบทวนสอบสินค้าและเรียกคืน (Traceability & Recall)

**สถานะ:** เขียนโค้ดครบและผ่านชุดทดสอบ 81 ข้อแล้ว · รอสร้างชีตจริงและ UAT
**เจ้าของระบบ:** QC · **ผู้ใช้ร่วม:** คลังสินค้า · จัดซื้อ · ขาย/โลจิสติกส์ · ผู้บริหาร
**ที่มาของความต้องการ:** ฟอร์ม QC 4 ใบ — FM-QC-TR-01/02 และ FM-QC-RC-01/02

---

## 1. โจทย์

ถ้าผู้ขายโทรมาบอกว่า *"อินเวอร์เตอร์ล็อต LOT-2607-A มีปัญหา PCB"* วันนี้ทีมต้องตอบให้ได้ภายในไม่กี่ชั่วโมงว่า

| คำถาม | ต้องตอบว่า |
|---|---|
| ล็อตนี้เรารับมากี่ตัว จากใคร PO ไหน | จำนวน · ผู้ขาย · เลข PO · เลขใบกำกับของผู้ขาย |
| ตอนนี้อยู่ในคลังกี่ตัว คลังไหน | ต้องกักทันทีก่อนที่ใครจะเบิกออกไป |
| ส่งลูกค้าไปแล้วกี่ตัว ใคร โครงการไหน ใบส่งของเลขอะไร | ต้องโทรหาให้ครบ ไม่ตกใคร |
| **รวมแล้วครบไหม** | รับเข้า = ส่งออก + คงคลัง — ถ้าไม่ครบ แปลว่ามีของที่เราตามไม่เจอ |

ปัจจุบันคำตอบเหล่านี้อยู่ใน SAP Business One อยู่แล้ว แต่กระจายใน 5–6 ตารางที่ต้อง join กันเอง
ทีม QC จึงต้องขอ IT ดึงรายงาน หรือคีย์ลงฟอร์ม Excel ซ้ำด้วยมือ ซึ่ง (ก) ช้า (ข) คีย์ผิดได้ (ค) ไม่มีใครรู้ว่าคีย์ครบหรือยัง

**ระบบนี้ทำหน้าที่เดียว: เปลี่ยนข้อมูลที่มีอยู่แล้วใน SAP ให้ตอบ 4 คำถามข้างบนได้ในหน้าจอเดียว แล้วคุมกระบวนการเรียกคืนจนจบ**

## 2. หลักการออกแบบ 4 ข้อ

### 2.1 SAP เป็นแหล่งความจริง ระบบนี้อ่านอย่างเดียว

```
SAP B1  ──────►  Traceability (Google Sheets)
      (อ่านอย่างเดียว · ไม่มีการเขียนกลับแม้แต่ field เดียว)
```

ตามหลักเดียวกับ [เอกสาร 09 §3.1](09-usability-and-sap.md) — ขอแค่สิทธิ์อ่าน อนุมัติง่ายกว่ามาก
และไม่มีทางทำข้อมูลใน B1 เสียหาย

### 2.2 ไม่ให้คนคีย์สิ่งที่ระบบคำนวณเองได้

ฟอร์ม FM-QC-TR-01 เดิมให้คนกรอก 23 คอลัมน์ต่อ 1 ซีเรียล — ล็อต 500 ชิ้นคือ 500 บรรทัด
ในระบบใหม่ ฟอร์มนี้กลายเป็น **รายงานที่กดออกได้** ไม่ใช่ฟอร์มที่ต้องกรอก

| ฟอร์มเดิม | ระบบใหม่ |
|---|---|
| FM-QC-TR-01 Traceability Master | ปุ่ม "ออกรายงาน" — สร้างแท็บพร้อมพิมพ์และเซ็น |
| FM-QC-RC-01 ช่อง "Affected Qty – In Stock / Delivered / Unaccounted" | คำนวณจาก SAP ทุกครั้งที่เปิดหน้า |
| FM-QC-RC-02 ตารางติดตามลูกค้า | ระบบไล่จาก SAP แล้วสร้างแถวให้ครบทุกปลายทาง |
| FM-QC-TR-02 Backward/Forward lines | ระบบสร้าง "จำนวนที่ควรหาเจอ" ให้ก่อน คนแค่ยืนยันของจริง |

**สิ่งที่ยังต้องให้คนกรอก คือสิ่งที่ระบบไม่รู้จริง ๆ:** ปัญหาคืออะไร · ระดับความเสี่ยง ·
สาเหตุที่แท้จริง · จะเรียกคืนหรือแก้หน้างาน · ลูกค้าตอบว่าอะไร · หลักฐานที่ใช้ยืนยัน

### 2.3 กระดูกสันหลังคือ `OITL` / `ITL1` ของ B1 ไม่ใช่ตารางที่เราสร้างเอง

B1 บันทึกการเดินของทุก lot/serial ไว้ใน Item Transaction Log อยู่แล้ว — ทุกครั้งที่ของเข้า ออก
โอน หรือคืน จะมี 1 แถวเสมอ ระบบนี้จึงไม่พยายามสร้างสมุดบัญชีสต๊อกของตัวเองซ้ำ
แค่คัดลอกตารางนั้นมาแล้วอ่านให้เป็นภาษาคน

> ผลที่ตามมาที่สำคัญ: **ระบบจะแม่นเท่าที่ B1 แม่น** ถ้าคลังตัดจ่ายโดยไม่ระบุล็อต ระบบก็ตามไม่เจอ
> เรื่องนี้อยู่ในความเสี่ยงข้อ 11.1

### 2.4 กักของก่อน แล้วค่อยสอบสวน

ลำดับการทำงานถูกบังคับด้วยสถานะของเคส — เปิดเคสปุ๊บ **ระบบสร้างรายการกักของในคลังให้ทันที**
ไม่ต้องรอผลสอบสวน เพราะของที่เบิกออกไประหว่างสอบสวนคือของที่ตามคืนยากที่สุด

## 3. โครงสร้างข้อมูล

Google Spreadsheet 1 ไฟล์ `MGS-TRACEABILITY-<ปี>` · 23 แท็บ แบ่ง 3 กลุ่มตามว่า**ใครเป็นเจ้าของ**

### 3.1 กลุ่ม A — กระจกเงาของ SAP (11 แท็บ) · sync ทับทุก 30 นาที · ระบบไม่แก้

| แท็บ | มาจากตาราง B1 | ใช้ทำอะไร |
|---|---|---|
| `SAP_Items` | `OITM` + `OITB` | รหัสสินค้า ยี่ห้อ และวิธีติดตาม (SERIAL / BATCH) |
| `SAP_BP` | `OCRD` | ผู้ขายและลูกค้า |
| `SAP_Warehouses` | `OWHS` | คลัง · `U_LocationType = CUSTOMER` ใช้แยกคลังหน้างานลูกค้า |
| `SAP_PO_Lines` | `OPOR` / `POR1` | ใบสั่งซื้อ — ปลายทางของการตามรอยย้อนกลับ |
| `SAP_GRPO_Lines` | `OPDN` / `PDN1` | ใบรับสินค้า — เชื่อม lot กลับไปหา PO และใบกำกับผู้ขาย |
| `SAP_Delivery_Lines` | `ODLN` / `DLN1` | ใบส่งของ — ต้นทางของการตามรอยไปข้างหน้า |
| `SAP_Invoice_Lines` | `OINV` / `INV1` | ใบกำกับขาย (อ้างอิงเลขที่) |
| `SAP_Return_Lines` | `ORDN`/`RDN1` + `ORPD`/`RPD1` | การคืนทั้งสองทิศ |
| `SAP_Lots` | `OBTN` + `OSRN` | ทะเบียนล็อตและซีเรียล · `LotNumber` = ล็อตของผู้ขาย |
| **`SAP_Lot_Moves`** | **`OITL` + `ITL1`** | **★ การเดินของทุก lot/SN — ตารางที่ระบบทั้งหมดตั้งอยู่บน** |
| `SAP_Lot_Stock` | `OIBT` + `OSRI` | คงคลังแยกล็อตต่อคลัง |

**คีย์ที่ผูกทุกอย่างเข้าด้วยกัน** คือ `lot_key = ItemCode + "|" + DistNumber` ตามหลักของ B1 เอง
(ล็อตเลขเดียวกันต่างสินค้า ถือเป็นคนละล็อต)

**กติกาของ `SAP_Lot_Moves`:** `quantity` เป็นค่าบวกเสมอ ทิศทางดูจาก `direction` (`IN`/`OUT`) เท่านั้น
ไม่ใช้เครื่องหมายลบเป็นตัวบอกทิศ เพราะเคยพลาดมาแล้วในระบบที่ปนกันสองแบบ

### 3.2 กลุ่ม B — ข้อมูลที่ MGS เป็นเจ้าของ (8 แท็บ) · sync ไม่แตะ

| แท็บ | ตรงกับฟอร์ม | 1 แถว = |
|---|---|---|
| `Recall_Cases` | FM-QC-RC-01 ส่วนหัว | 1 เคส |
| `Recall_Scope` | RC-01 §Affected Lot/SN | 1 ล็อตหรือ 1 ซีเรียลที่กระทบ |
| `Recall_Tracking` | **FM-QC-RC-02** | 1 ปลายทาง (ลูกค้า/โครงการ/คลัง) |
| `Recall_Actions` | RC-01 §Investigation + §Decision | 1 หัวข้อ CAPA หรือ 1 การตัดสินใจ |
| `Holds` | RC-01 "HOLD affected stock" | 1 การกัก (ล็อต × คลัง) |
| `Mock_Recalls` | FM-QC-TR-02 ส่วนหัว | 1 การทดสอบ |
| `Mock_Recall_Lines` | TR-02 Backward/Forward | 1 จุดที่ต้องไปยืนยัน |
| `Trace_Notes` | TR-01 คอลัมน์ MGS Lot / Remark | หมายเหตุของ QC ต่อ 1 ล็อต |

> **ทำไม `Trace_Notes` ต้องแยกออกมา:** ถ้าเก็บหมายเหตุของ QC ไว้ในแท็บ SAP_* รอบ sync
> ครั้งถัดไปจะทับหายทันที นี่คือกับดักที่ระบบซิงก์สองทางเจอเสมอ จึงแยกโดยตั้งใจ

## 4. สามคำถามที่ระบบตอบ

### 4.1 ตามรอยย้อนกลับ — ของล็อตนี้มาจากไหน

```
lot_key ─► SAP_Lot_Moves (direction = IN)
              └─ obj_type 20 (ใบรับสินค้า) ─► SAP_GRPO_Lines
                                                 ├─ num_at_card    = ใบกำกับของผู้ขาย
                                                 └─ base_entry ─► SAP_PO_Lines = เลข PO
```
ได้ผลลัพธ์: ผู้ขาย · เลข PO · เลขใบกำกับ · วันที่รับ · คลังที่รับเข้า · ล็อตของผู้ขาย

### 4.2 ตามรอยไปข้างหน้า — ของล็อตนี้ไปอยู่ที่ไหน

```
lot_key ─┬─► SAP_Lot_Moves (direction = OUT, obj_type 15/13) = ลูกค้า · โครงการ · เลข DO · วันที่
         └─► SAP_Lot_Stock                                   = คลังไหน เหลือเท่าไร
```

### 4.3 กระทบยอด — ครบหรือไม่ครบ

```
รับเข้า + ลูกค้าคืน  −  ส่งลูกค้า  −  คืนผู้ขาย  −  ตัดออก/ทำลาย  −  คงคลัง  =  ส่วนต่าง
```
**ส่วนต่างต้องเป็น 0** ถ้าไม่เป็นศูนย์ = มีของที่ระบบระบุที่อยู่ไม่ได้ และหน้าจอขึ้นเตือนสีแดงทันที
(การโอนย้ายคลัง `obj_type 67` ไม่ถูกนับ เพราะไม่เปลี่ยนยอดรวม)

**นี่คือตัวเลขที่มีค่าที่สุดในระบบ** — เพราะมันบอกล่วงหน้าว่าถ้าเกิดเรื่องจริง เราจะตามของไม่เจอกี่ชิ้น
โดยไม่ต้องรอให้เกิดเรื่องก่อน

### 4.4 ค้นหา — พิมพ์อะไรมาก็ต้องเจอ

คนหน้างานไม่ได้ถือ `lot_key` มา เขาถือสิ่งที่อยู่ตรงหน้า ระบบจึงค้นจากทุกอย่างนี้ได้:
หมายเลขซีเรียล · เลขล็อต · ล็อตของผู้ขาย · ซีเรียลผู้ผลิต · รหัส/ชื่อสินค้า ·
เลขใบส่งของ · เลขใบรับ · เลข PO · เลขใบกำกับผู้ขาย · ชื่อ/รหัสลูกค้า · ชื่อโครงการ

และตัดขีดกับช่องว่างออกก่อนเทียบ — `sg50ra001` เจอ `SG50R-A001`

## 5. โฟลว์เคสเรียกคืน

```
DRAFT ──► OPEN ──► CONTAINED ──► TRACKING ──► VERIFYING ──► CLOSED
             └──────────┴──► CANCELLED
```

| สถานะ | เกิดอะไรขึ้น | เงื่อนไขที่จะไปขั้นถัดไป |
|---|---|---|
| **OPEN** | ระบบคำนวณของที่กระทบ · **กักของในคลังอัตโนมัติ** · สร้างแถวติดตามทุกปลายทาง · แจ้ง Lark | ของในคลังถูกกักครบ |
| **CONTAINED** | ยืนยันแล้วว่าไม่มีของหลุดออกจากคลังได้อีก | — |
| **TRACKING** | ติดต่อลูกค้าและโครงการ บันทึกจำนวนที่คืน/เปลี่ยน/แก้ไข | ทุกแถวติดตามปิดครบ |
| **VERIFYING** | ตรวจ % ประสิทธิผล และปลดการกักที่ไม่จำเป็น | ของครบ · ไม่มีของค้างกัก · การตัดสินใจสรุปครบ |
| **CLOSED** | ปิดถาวร แก้ไขไม่ได้ | — |
| **CANCELLED** | ใช้เมื่อพิสูจน์ว่าไม่มีปัญหาจริง — **ปลดการกักทั้งหมดอัตโนมัติ** | — |

### 5.1 การรวมแถวติดตาม — จุดที่ต่างจากฟอร์มกระดาษอย่างมีนัยสำคัญ

เรียกคืนซีเรียล 20 ตัวที่กระจายอยู่ 3 ที่ ระบบสร้าง **3 แถว ไม่ใช่ 20 แถว**

| ปลายทาง | ช่วงซีเรียล | จำนวน | ต้องทำ |
|---|---|---|---|
| คลังฉะเชิงเทรา | SG50R-A001–A005 | 5 | กักไว้ |
| Customer A / Project A (DO-260812) | SG50R-A006–A012 | 7 | ตรวจ/แก้ไขหน้างาน |
| Customer B / Project B (DO-260815) | SG50R-A013–A020 | 8 | ตรวจ/แก้ไขหน้างาน |

เหตุผล: การเรียกคืนจากลูกค้า 2 ราย คือการโทร 2 สาย ไม่ใช่ 20 สาย — ตรงกับที่ทีมเขียนในฟอร์ม RC-02 เดิมอยู่แล้ว
(ระบบยังเก็บซีเรียลรายตัวไว้ใน `Recall_Scope` ครบ สำหรับตอนตรวจสอบ)

### 5.2 การกระทบยอดบางส่วนของล็อตใหญ่

ล็อตราง 500 เส้นที่กระทบแค่ 100 เส้น ระบบจะไม่เรียกคืนทั้งล็อต — คำนวณสัดส่วน `100/500 = 20%`
แล้วกระจายตามปลายทางจริง ไม่ใช่เหมารวม

### 5.3 กฎที่ระบบบล็อกให้ (ทดสอบครบทุกข้อแล้ว)

| # | กฎ | กันอะไร |
|---|---|---|
| 1 | จำนวนที่คืน+เปลี่ยน+แก้ไข ห้ามเกินจำนวนที่กระทบ | ตัวเลขประสิทธิผลเกิน 100% |
| 2 | ปิดแถวติดตามไม่ได้ถ้ายังมีของค้าง | ติ๊ก "เสร็จสิ้น" ทั้งที่ของยังอยู่หน้างาน |
| 3 | ปิดเคสไม่ได้ถ้ายังมีของถูกกัก | ของค้างสถานะกักโดยไม่มีเจ้าของ |
| 4 | ปิดเคสไม่ได้ถ้าการตัดสินใจยังไม่สรุปครบ | เคสปิดโดยไม่มีคำตอบว่าเคลมผู้ขายหรือยัง |
| 5 | ผู้กรอกกับผู้อนุมัติต้องคนละคน | อนุมัติงานตัวเอง |
| 6 | ผู้ทดสอบกับผู้ทบทวน mock recall ต้องคนละคน | ตรวจงานตัวเอง |
| 7 | ปลดการกักต้องระบุเหตุผล ≥ 5 ตัวอักษร | ปลดแล้วไม่มีใครรู้ว่าทำไม |
| 8 | เปลี่ยนสถานะข้ามขั้นไม่ได้ · ปิดแล้วเปิดใหม่ไม่ได้ | แท็บเก่าที่เปิดค้างไว้ย้อนสถานะ |
| 9 | ระบุช่วงซีเรียลที่ไม่มีจริงใน SAP ถูกปฏิเสธ | เดาเลขซีเรียลที่ไม่มีตัวตน |
| 10 | คำอธิบายปัญหาสั้นกว่า 10 ตัวอักษรถูกปฏิเสธ | "เสีย" แล้วส่งเข้ากลุ่ม Lark |
| 11 | ตั้งหัวข้อ CAPA เป็น "เสร็จ" โดยไม่กรอกรายละเอียดไม่ได้ | ช่องว่างในเอกสารตอน audit |

## 6. การทดสอบทวนสอบย้อนกลับ (Mock Recall)

**หลักที่ยึด: ระบบสร้าง "จำนวนที่ควรหาเจอ" ให้ แต่คนต้องไปยืนยันของจริง**
ถ้าให้ระบบตอบเองทั้งหมด การทดสอบก็ไม่ได้พิสูจน์อะไรเลย — มันจะพิสูจน์แค่ว่าระบบอ่านตัวเองได้

| ขั้น | ใครทำ |
|---|---|
| เลือกล็อต กดเริ่ม — **ระบบเริ่มจับเวลาทันที** | QC |
| เดินไปยืนยันแต่ละจุดว่าหาเจอกี่หน่วย พร้อมหลักฐาน | QC + คลัง |
| กดปิดผล — ระบบคำนวณและตัดสิน | QC |
| ทบทวนผล + CAPA เมื่อไม่ผ่าน | ผู้จัดการคุณภาพ (คนละคนกับผู้ทดสอบ) |

**เกณฑ์ผ่าน — ต้องผ่านครบทั้ง 3 ข้อ**
1. หาเจอครบ 100% ของจำนวนที่คาดไว้
2. กระทบยอดลงตัว (ส่วนต่าง = 0)
3. ใช้เวลาไม่เกินเป้า (ค่าตั้งต้น 120 นาที · แก้ได้ในแท็บ `Settings`)

ไม่ผ่าน = ระบบบังคับให้ระบุสาเหตุ การแก้ไข ผู้รับผิดชอบ และกำหนดเสร็จ ก่อนจะทบทวนได้
และระบบเตือนทุกวันที่ 1 ถ้าไม่ได้ทดสอบเกิน 180 วัน

### 7.1 อุปสรรคและทางแก้

Apps Script อยู่บนคลาวด์ เรียกเข้าเครื่องในออฟฟิศไม่ได้ จึงกลับทิศ — ให้ตัวส่งที่รันในออฟฟิศ
"ผลัก" ข้อมูลออกไปแทน **ไม่ต้องเปิดพอร์ตขาเข้าเลยแม้แต่พอร์ตเดียว**

| ไฟล์ | ใช้ทำอะไร |
|---|---|
| `apps-script/traceability/sap-push-agent.ps1` | ตัวส่ง PowerShell ~300 บรรทัด ตั้งเวลาด้วย Task Scheduler |
| `apps-script/traceability/sap-push-config.example.json` | แม่แบบคอนฟิก (คัดลอกแล้วแก้ · ไฟล์จริงถูก gitignore) |
| `05_Sap.gs` ฟังก์ชัน `printSapQueries()` | พิมพ์ SQL ทั้งชุดให้ผู้ดูแล B1 ตรวจก่อนอนุมัติ |

### 7.2 ความปลอดภัยของ endpoint

| มาตรการ | รายละเอียด |
|---|---|
| ลายเซ็น HMAC-SHA256 | ทุก request เซ็น `timestamp . body` ด้วยกุญแจลับ · เทียบแบบ timing-safe |
| อายุคำขอ 5 นาที | กันการดักจับแล้วส่งซ้ำ (replay) |
| allowlist แท็บ | เขียนได้เฉพาะ 11 แท็บ `SAP_*` — ยิงมาที่ `Recall_Cases` ถูกปฏิเสธ |
| ตรวจก่อนเขียน | แถวไหนขาดฟิลด์บังคับ = ปฏิเสธ**ทั้งแท็บ** ไม่เขียนครึ่ง ๆ กลาง ๆ |
| เพดาน 5,000 แถว/ครั้ง | ตารางใหญ่ส่งเป็นก้อน: ก้อนแรก `REPLACE` ที่เหลือ `APPEND` |
| กุญแจอยู่ใน Script Properties | ไม่อยู่ในซอร์ส เพราะซอร์สถูกคัดลอกไปอยู่ในแชทและไดรฟ์เสมอ |

> ⚠️ **endpoint นี้ต้อง deploy เป็นโปรเจกต์ Apps Script แยกอีกตัว** ที่ผูกกับสเปรดชีตเดียวกัน
> เพราะมันต้องตั้งเป็น "เข้าถึงได้โดยทุกคน" ส่วนเว็บแอปหลักต้องจำกัดเฉพาะโดเมนบริษัท
> **ห้ามเปิดเว็บแอปหลักให้คนนอกเข้าถึงเด็ดขาด**

### 7.3 ทางเลือกที่ปลอดภัยกว่า (แนะนำถ้า IT ทำได้)

ให้ตัวส่งเขียนลงชีตตรงผ่าน **Google service account** + Sheets API แทนการมี endpoint สาธารณะ
ข้อดี: ไม่มี URL ให้ใครยิงได้เลย · ข้อเสีย: ต้องตั้ง service account และจัดการ JSON key
ถ้าเลือกทางนี้ ให้ตัวส่งเขียนแท็บ `SAP_*` ตรง แล้วปล่อยให้ trigger รายชั่วโมงตรวจความสดของข้อมูลแทน

### 7.4 เมื่อ sync ล่ม

ระบบไม่หยุดทำงาน — ขึ้นแถบเหลืองบนทุกหน้าจอว่า *"ข้อมูลจาก SAP ล่าสุด 08:30 (95 นาทีที่แล้ว)
ตัวเลขที่เห็นอาจไม่ทันปัจจุบัน"* และแจ้ง Lark ครั้งเดียว (ไม่รบกวนซ้ำ) แล้วแจ้งอีกครั้งเมื่อกลับมาปกติ

## 8. บทบาทและสิทธิ์

สิทธิ์มาจากอีเมลในแท็บ `Users` เท่านั้น และ**ตรวจที่เซิร์ฟเวอร์ทุกครั้ง** — การซ่อนปุ่มบนหน้าจอเป็น UX ไม่ใช่การกันสิทธิ์

| บทบาท | ทำอะไรได้ |
|---|---|
| `QC` | เปิดเคส · กรอกสอบสวน · บันทึกติดตาม · กักของ · ทดสอบทวนสอบ |
| `QCM` ผู้จัดการคุณภาพ | ทุกอย่างของ QC + **อนุมัติ CAPA · ปลดการกัก · ปิดเคส · ยกเลิกเคส · ทบทวนผลทดสอบ** |
| `WH` คลัง | บันทึกผลติดตามของฝั่งคลัง · แจ้งกักของ (ปลดไม่ได้) |

**การถอนสิทธิ์เมื่อพนักงานลาออก:** ตั้ง `is_active = FALSE` ในแท็บ `Users` — มีผลภายใน 10 นาที (cache)


## 11. ความเสี่ยงที่ยอมรับและข้อจำกัด

### 11.1 ระบบแม่นเท่าที่ B1 แม่น ⚠️ ข้อสำคัญที่สุด

ถ้าคลังตัดจ่ายโดยไม่ระบุล็อต หรือรับเข้าโดยไม่ผูกซีเรียล ระบบนี้ก็ตามไม่เจอเช่นกัน
**ช่อง "ระบุที่อยู่ไม่ได้" คือเครื่องวัดวินัยการคีย์ล็อตของคลัง** — ควรดูตัวเลขนี้ก่อนตัดสินใจว่าระบบพร้อมใช้จริงหรือยัง
ถ้าตัวเลขนี้ไม่เป็น 0 ในล็อตส่วนใหญ่ ปัญหาอยู่ที่กระบวนการหน้างาน ไม่ใช่ที่ระบบ

### 11.2 ข้อจำกัดอื่น

| เรื่อง | สถานะ |
|---|---|
| ข้อมูลช้าได้ถึง 30 นาที | ยอมรับ — เคสเรียกคืนใช้เวลาเป็นชั่วโมง ไม่ใช่วินาที · ปุ่ม "สร้างรายการติดตามใหม่" ดึงซ้ำได้เมื่อจำเป็น |
| ดึงย้อนหลัง 3 ปี | ตั้งได้ที่ `YearsBack` ในคอนฟิกตัวส่ง · เกินนี้ต้องดูเรื่องขนาดชีต |
| `SAP_Lot_Moves` เกิน ~50,000 แถว | ชีตจะเริ่มช้า — ต้องย้ายข้อมูลเก่าไปแท็บ archive (ยังไม่ได้ทำ) |
| ยังไม่มีการแนบรูปในแอปมือถือ | โครงสร้าง `apiUploadEvidence` พร้อมแล้ว แต่หน้าจอยังไม่มีปุ่ม — เพิ่มได้ใน Phase ถัดไป |
| ยังไม่ได้ทดสอบบนมือถือจริง | ออกแบบไว้แล้ว (ปุ่ม ≥ 44px · ตัวอักษร 16px · ไม่มี hover) แต่ต้องทดสอบจริงก่อนขึ้นระบบ |
| การแจ้ง Lark ต้องตั้ง webhook เอง | ถ้าไม่ตั้ง ระบบทำงานปกติทุกอย่าง แค่ไม่มีแจ้งเตือน |
